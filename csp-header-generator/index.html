Violation Reporting

Report-URI and Report-To

CSP supports two reporting mechanisms. The older report-uri directive sends JSON violation reports via POST to a specified URL. The newer report-to directive uses the Reporting API and requires a Report-To response header defining endpoint groups.

For maximum compatibility, include both directives in your policy.

Violation Report Format

When a CSP violation occurs, the browser sends a JSON report containing:

{ "csp-report": { "document-uri": "https://example.com/page", "referrer": "", "violated-directive": "script-src 'self'", "effective-directive": "script-src", "original-policy": "default-src 'self'; script-src 'self';", "blocked-uri": "https://evil.com/malicious.js", "status-code": 200, "source-file": "https://example.com/page", "line-number": 15, "column-number": 2 } }

The blocked-uri field shows which resource was blocked, violated-directive indicates which policy rule was triggered, and source-file with line/column numbers help pinpoint the offending code. Use a service like report-uri.com or build your own endpoint to collect and analyze these reports.

Report-To Configuration

Report-To: {"group":"csp","max_age":86400,"endpoints":[{"url":"https://example.com/csp-report"}]} Content-Security-Policy: default-src 'self'; report-to csp;

CSP Reference Guide

What Is Content Security Policy?

Content Security Policy (CSP) is a security standard introduced to mitigate cross-site scripting (XSS) and other content injection attacks. By declaring which resource origins are permitted, you create a whitelist that browsers enforce. Any resource loaded from an unlisted origin is blocked.

CSP was first standardized by the W3C and is now supported by all major browsers. The OWASP Content Security Policy guide is an authoritative reference for implementation best practices.

Directive Reference

Each CSP directive controls a specific type of resource:

  • default-src — Fallback for all unspecified directives
  • script-src — JavaScript sources (critical for XSS prevention)
  • style-src — CSS stylesheet sources
  • img-src — Image sources
  • font-src — Web font sources
  • connect-src — XHR, fetch, WebSocket endpoints
  • media-src — Audio and video sources
  • object-src — Plugin content (Flash, Java)
  • frame-src — iframe sources
  • frame-ancestors — Which pages can embed this page (replaces X-Frame-Options)
  • base-uri — Restricts the base element URL
  • form-action — Where forms can submit to

For the full specification, see MDN's CSP documentation and the Wikipedia CSP article.

Nonces and Hashes

Instead of using 'unsafe-inline', you can whitelist specific inline scripts/styles using:

  • Nonces: A unique, random token generated per request. Add nonce-{random} to your CSP and the matching nonce attribute to your script/style tag.
  • Hashes: A SHA-256/384/512 hash of the inline script content. The browser computes the hash and checks it against the policy.

Nonces are preferred for dynamic applications since hashes break when code changes. With 'strict-dynamic', nonce-trusted scripts can load additional scripts without explicit allowlisting.

Browser Compatibility

CSP Level 2 is supported in Chrome 40+, Firefox 31+, Safari 10+, and Edge 15+. CSP Level 3 features like 'strict-dynamic' are supported in Chrome 52+, Firefox 52+, and Edge 79+. Safari has partial Level 3 support. This generator tool works in all modern browsers including mobile Chrome and Safari on iOS/Android.

Privacy Note: All CSP generation and evaluation happens entirely in your browser. No data is sent to any server. Your policies and configurations never leave your device.

Frequently Asked Questions

What is a Content Security Policy (CSP)?
A Content Security Policy is an HTTP response header that tells browsers which content sources are allowed on a web page. It prevents cross-site scripting (XSS), clickjacking, and other code injection attacks by restricting where scripts, styles, images, and other resources can be loaded from.
How do I add a CSP header to my website?
You can add a CSP header via your web server configuration (Nginx, Apache), your application framework (Express, Django, Rails), or as a meta tag in your HTML. The server header approach is preferred because meta tags cannot set frame-ancestors or report-uri directives.
What does 'unsafe-inline' mean in CSP?
'unsafe-inline' allows inline scripts and styles (e.g., onclick handlers, style attributes, script tags without src). It significantly weakens CSP protection because any injected inline code will execute. Prefer using nonces or hashes instead of unsafe-inline for better security.
What is the difference between CSP Level 2 and Level 3?
CSP Level 2 added nonce-based and hash-based source expressions and the base-uri and form-action directives. CSP Level 3 introduced strict-dynamic, which automatically trusts scripts loaded by already-trusted scripts, and the report-to directive using the Reporting API. Most modern browsers support Level 3.
Should I use 'strict-dynamic' in my CSP?
strict-dynamic is recommended for applications that dynamically load scripts. When combined with a nonce, it allows trusted scripts to load additional scripts without listing every domain. It is the foundation of the strict CSP approach recommended by security researchers.
What happens when a CSP violation occurs?
When a browser detects a resource that violates the CSP, it blocks that resource from loading or executing. If a report-uri or report-to directive is configured, the browser sends a JSON violation report to the specified endpoint. The Content-Security-Policy-Report-Only header can be used to monitor violations without blocking.
