Understanding Content Security Policy

Content Security Policy (CSP) is one of the most effective defenses against cross-site scripting (XSS) attacks, the most prevalent class of web application vulnerabilities. CSP works by telling the browser exactly which sources of content are trusted, and the browser refuses to load or execute anything that does not match the policy.

How CSP Works

When a browser receives a CSP header with an HTTP response, it parses each directive and builds an allow-list of trusted sources for each content type. When the page tries to load a resource (script, stylesheet, image, etc.), the browser checks it against the relevant directive. If no matching source is found, the browser blocks the resource and optionally sends a violation report to a configured endpoint.

Directive Hierarchy

The default-src directive acts as a fallback for any directive that is not explicitly configured. For example, if you set default-src 'self' but do not specify img-src, then images will also be restricted to same-origin. Specific directives always override the default. This makes default-src 'none' a popular starting point for strict policies, where you then selectively enable each content type.

Source Values Explained

  • 'self' — Allows resources from the same origin (same scheme, host, and port).
  • 'none' — Blocks all sources for this directive. Use with default-src for a deny-by-default approach.
  • 'unsafe-inline' — Allows inline scripts/styles. Weakens XSS protection significantly.
  • 'unsafe-eval' — Allows eval() and similar dynamic code execution. Avoid when possible.
  • 'strict-dynamic' — Trusts scripts loaded by already-trusted scripts. Useful for modern frameworks.
  • nonce-<value> — Allows specific inline scripts/styles with a matching nonce attribute.
  • sha256-<hash> — Allows inline code whose hash matches the specified value.
  • Domain URLs — Allows resources from the specified domain(s), e.g., https://cdn.example.com.

Deployment Strategy

The recommended approach is to deploy CSP in stages: (1) Start with Content-Security-Policy-Report-Only and a report endpoint. (2) Monitor violation reports and adjust the policy. (3) Once violations are resolved, switch to the enforcing Content-Security-Policy header. This approach prevents accidentally breaking your site while building a strong policy.

Common Use Cases & Tips

Single-Page Applications SPAs often need connect-src for API calls, script-src for bundles, and style-src for CSS. Use 'strict-dynamic' with nonces to allow dynamically loaded scripts securely.
E-Commerce Sites Payment pages benefit from strict CSP to prevent data skimming. Lock down script-src and connect-src to only trusted payment processors and your own origin.
WordPress & CMS Sites CMS platforms often use inline styles and scripts. Start with a moderate policy and progressively tighten it. Consider using nonces with a server-side plugin.
API-Only Services APIs that do not serve HTML can use a minimal CSP like default-src 'none' to add defense-in-depth against accidental HTML responses.
Embedding Prevention Use frame-ancestors 'none' to prevent your pages from being embedded in iframes on other sites, mitigating clickjacking attacks.
Third-Party Widget Integration When adding analytics, chat widgets, or ad scripts, add their domains to the appropriate directives (script-src, connect-src, frame-src) rather than using unsafe-inline.

Browser Compatibility

Content Security Policy Level 2 is supported by all modern browsers including Chrome 40+, Firefox 31+, Safari 10+, Edge 15+, and Opera 27+. CSP Level 3 features like strict-dynamic and worker-src are supported in Chrome 52+, Firefox 52+, Safari 15.4+, and Edge 79+.
