Common CORS Patterns

Reference configurations for typical deployment architectures.

SPA + API (different ports)

React/Vue on :3000 calling an API on :8080 during development.

Access-Control-Allow-Origin: http://localhost:3000 Access-Control-Allow-Methods: GET, POST, PUT, DELETE Access-Control-Allow-Headers: Content-Type, Authorization Access-Control-Allow-Credentials: true

CDN serving static assets

Fonts and images served from a CDN to multiple domains.

Access-Control-Allow-Origin: * Access-Control-Max-Age: 86400

Multi-origin API

An API allowing requests from several specific domains. Origin must be validated server-side.

# Server-side pseudocode: allowed = ["https://app.com", "https://admin.app.com"] if request.origin in allowed: set_header("Access-Control-Allow-Origin", request.origin) set_header("Vary", "Origin")

Wildcard + Credentials (FAILS)

This combination is explicitly forbidden by the CORS specification and will always be rejected.

/* THIS WILL NOT WORK */ Access-Control-Allow-Origin: * Access-Control-Allow-Credentials: true /* Browser error: Cannot use wildcard when credentials flag is true. */

Browser DevTools Debugging Guide

Step-by-step instructions for diagnosing CORS issues using browser developer tools.

Open the Network tab

Press F12 or Cmd+Opt+I (macOS) / Ctrl+Shift+I (Windows/Linux) to open DevTools, then select the Network tab.

Reproduce the failed request

Trigger the action that causes the CORS error. The failed request will appear highlighted in red in the network panel.

Look for a preflight OPTIONS request

Filter by "method:OPTIONS" or scan for an OPTIONS request to the same URL. If present, it must return status 200 or 204 with the correct Access-Control headers.

Inspect the response headers

Click the request, go to the Headers tab, and check the Response Headers. Verify that Access-Control-Allow-Origin matches your origin and that required methods/headers are listed.

Read the console error message

Switch to the Console tab. The CORS error message tells you exactly what is missing. Copy it and use the Error Decoder above for a clear explanation.

Verify with curl

Use the Curl Generator above to test the server directly. If curl returns correct CORS headers but the browser blocks, the issue may be in your client-side fetch configuration (missing credentials mode, wrong content type, etc.).

Security Implications of CORS

CORS is a security mechanism. Misconfiguration can expose your API to attacks. Understand the risks before loosening restrictions.

  • Access-Control-Allow-Origin: * allows any website to read responses from your API. Never use this for endpoints that return private data or require authentication.
  • Reflecting the Origin header without validation is equivalent to using * but worse — it also works with credentials. Always validate against a whitelist.
  • Allow-Credentials: true means the browser sends cookies and auth headers cross-origin. Combined with a misconfigured origin, any site can impersonate authenticated users.
  • Exposing sensitive headers via Access-Control-Expose-Headers can leak internal details. Only expose headers the client genuinely needs.
  • Long Max-Age values cache preflight responses. If you change your CORS policy, browsers may use the old cached response for up to that duration.
  • CORS does not replace authentication. CORS controls which origins can read responses — it does not prevent requests from being sent. Server-side authorization is always required.

For a thorough understanding of the CORS specification, see the MDN CORS documentation and the Wikipedia article on CORS.

Frequently Asked Questions

What is CORS and why do I get CORS errors?
CORS (Cross-Origin Resource Sharing) is a browser security mechanism that restricts web pages from making requests to a different domain than the one serving the page. You get CORS errors when a server does not include the proper Access-Control-Allow-Origin header in its response, so the browser blocks the request to protect users from potential cross-site attacks. The request is actually sent and the server processes it — the browser simply refuses to let your JavaScript read the response.
What is a CORS preflight request?
A preflight request is an HTTP OPTIONS request the browser automatically sends before certain cross-origin requests. It happens when the request uses methods other than GET, HEAD, or POST, uses custom headers, or sends a Content-Type other than application/x-www-form-urlencoded, multipart/form-data, or text/plain. The server must respond with the appropriate Access-Control-Allow headers for the actual request to proceed. Use the flowchart above to check your specific case.
Why can't I use a wildcard (*) with credentials?
The CORS specification explicitly forbids using Access-Control-Allow-Origin: * when credentials (cookies, HTTP authentication, or client-side certificates) are included. When Access-Control-Allow-Credentials is true, the server must echo the exact requesting origin. This prevents exposing authenticated resources to arbitrary websites. The server needs to dynamically set the origin after validating it against a whitelist.
How do I fix the 'No Access-Control-Allow-Origin header' error?
Add the Access-Control-Allow-Origin header to your server's response. Set it to the specific origin making requests (e.g., https://example.com) or use * to allow all origins (only if credentials are not needed). The configuration varies by server — use the Config Generator above to get the exact code for Nginx, Apache, Express, Flask, Django, Spring Boot, ASP.NET, Go, or PHP.
Does this tool send my data to a server?
No. This tool runs entirely in your browser. Header building, configuration generation, error decoding, and preflight simulation are all performed client-side using JavaScript. No data is transmitted to any external server. You can verify this by opening the Network tab in DevTools and confirming that no requests are made while using the tool.
What is the difference between simple and preflighted CORS requests?
Simple requests use only GET, HEAD, or POST methods with standard headers and safe content types — the browser sends them directly with an Origin header. Preflighted requests use other methods, custom headers, or non-standard content types — the browser first sends an OPTIONS request to verify the server allows the actual request. See the MDN documentation on simple requests for the complete criteria.

About This Tool

The CORS Tester is a comprehensive browser-based tool designed to help web developers understand, debug, and configure Cross-Origin Resource Sharing (CORS) headers. CORS is a critical security mechanism implemented by all modern browsers that controls how web pages on one domain can request resources from a different domain. Misconfigured CORS headers are one of the most common sources of frustration in web development, often resulting in cryptic browser console errors.

This tool provides an interactive header builder that generates the correct Access-Control response headers in real time, a server configuration generator that produces copy-paste-ready code for nine server platforms (Nginx, Apache, Express.js, Flask, Django, Spring Boot, ASP.NET, Go, and PHP), an error decoder that translates opaque browser error messages into plain-language explanations with fixes, a preflight request simulator that shows exactly what the browser sends and expects, and a request/response header inspector that validates whether a given pair of headers would pass or fail CORS checks.

Built by Michael Lip, this tool runs entirely in the browser with no server-side component. All header building, configuration generation, error decoding, and preflight simulation happen locally using JavaScript. No data is ever transmitted to any external server, making it safe to use with production URLs and real authentication headers.
