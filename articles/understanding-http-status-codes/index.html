Why HTTP Status Codes Matter

Every time you click a link, submit a form, or load a page, your browser sends an HTTP request to a server. That server responds with a three-digit number that tells the browser exactly what happened. That number is the HTTP status code, and understanding it is one of the most practical skills you can develop as a web developer, system administrator, or API designer.

I have spent years debugging production systems, and I can tell you that the status code is always the first thing I look at when something goes wrong. It is the handshake between client and server, the first line of communication that either confirms everything is working or signals exactly where the failure occurred. A developer who understands status codes can diagnose issues in seconds that might otherwise take hours of digging through logs.

HTTP status codes were formalized in RFC 2616 (HTTP/1.1) and have been extended through various RFCs since then. The system is elegant in its simplicity: the first digit of the three-digit code tells you the category of response, and the remaining two digits provide specificity within that category. There are five categories in total, each representing a fundamentally different type of response.

This guide covers every standard HTTP status code you will encounter in the real world. For each one, I provide the official definition, a real-world scenario where you would see it, and practical debugging advice. Whether you are building REST APIs, troubleshooting server configurations, or optimizing for search engines, this reference will serve you well.

How Status Codes Work

When a client (typically a browser or API consumer) makes an HTTP request, the server processes that request and returns a response. The very first line of that response is the status line, which contains three pieces of information: the HTTP protocol version, the status code, and a human-readable reason phrase.

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 15234
Date: Tue, 25 Mar 2026 10:30:00 GMT

The status code 200 and the reason phrase OK tell the client that the request was successful. The reason phrase is purely informational and is often ignored by automated clients. What matters is the numeric code.

The five categories break down as follows:

Range Category Meaning
100-199InformationalRequest received, processing continues
200-299SuccessRequest received, understood, and accepted
300-399RedirectionFurther action needed to complete the request
400-499Client ErrorRequest contains an error on the client side
500-599Server ErrorServer failed to fulfill a valid request

This categorization system means you can immediately understand the nature of any response just by looking at the first digit. If you see a 4xx code, you know the client did something wrong. If you see a 5xx code, you know the server has a problem. This distinction is critical for debugging because it tells you where to look first.

1xx Informational Responses

The 1xx class of status codes indicates that the server has received the request headers and the client should continue with the request body, or that the server is still processing. These codes are relatively rare in everyday web development, but they play important roles in specific protocols and optimization scenarios.

100 Continue

The 100 Continue status tells the client that the initial part of the request has been received and the client should proceed with sending the request body. This code exists as an optimization for large request bodies. When a client wants to send a large payload (say, a 500 MB file upload), it can first send just the headers with an Expect: 100-continue header. The server checks the headers (authentication, content type, size limits) and responds with 100 Continue if everything looks acceptable, or with a 4xx error if not. This prevents the client from wasting bandwidth uploading a large file that the server would have rejected anyway.

Real-world scenario

A user uploads a 2 GB video file through your web application. The browser sends the request headers first, including Expect: 100-continue and Content-Length: 2147483648. Your server checks that the user is authenticated and that the file size is within your 5 GB limit, then responds with 100 Continue. The browser proceeds with the upload. If the user's session had expired, the server would respond with 401 Unauthorized instead, saving the user from waiting for a 2 GB upload to complete before learning that they need to log in again.

101 Switching Protocols

This status code indicates that the server is changing the protocol as requested by the client. The most common use is the WebSocket handshake. When a client wants to establish a WebSocket connection, it sends an HTTP upgrade request. The server responds with 101 Switching Protocols to confirm the protocol change, and all subsequent communication on that connection uses the WebSocket protocol instead of HTTP.

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

102 Processing (WebDAV)

The 102 Processing code is specific to WebDAV (Web Distributed Authoring and Versioning). It tells the client that the server has received the request and is working on it, but no response is available yet. This prevents the client from timing out during long-running WebDAV operations like recursive directory copies. You will rarely encounter this outside of WebDAV environments.

103 Early Hints

The 103 Early Hints status is a relatively recent addition (RFC 8297) that allows servers to send preliminary response headers before the final response is ready. The primary use case is sending Link headers that tell the browser to preload resources like CSS files, fonts, or JavaScript bundles while the server is still generating the main response. This can shave hundreds of milliseconds off perceived page load times because the browser starts fetching critical resources earlier in the loading process.

HTTP/1.1 103 Early Hints
Link: </styles/main.css>; rel=preload; as=style
Link: </scripts/app.js>; rel=preload; as=script

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Link: </styles/main.css>; rel=preload; as=style

2xx Success Responses

The 2xx class is what you want to see. These codes confirm that the client's request was successfully received, understood, and processed. While 200 is the most common, each 2xx code communicates a slightly different outcome that matters for proper API design and client behavior.

200 OK

The 200 OK status is the standard response for a successful HTTP request. The meaning varies depending on the request method. For a GET request, it means the resource has been fetched and is included in the response body. For a POST request, it means the action described in the request body has been carried out and the response body contains the result. This is by far the most common status code on the web.

Debugging tip: If you are getting 200 OK responses but your application is not working correctly, the problem is in the response body, not the HTTP layer. Check the Content-Type header to make sure it matches what your client expects, and inspect the response body for error messages that the server might be embedding inside a 200 response. Some APIs unfortunately return errors inside 200 responses instead of using proper status codes.

201 Created

The 201 Created status indicates that a new resource has been created as a result of the request. This is the correct response for a successful POST request that creates a new entity. The response should include a Location header pointing to the URL of the newly created resource, and optionally the resource itself in the response body.

POST /api/users HTTP/1.1
Content-Type: application/json

{"name": "Jane Doe", "email": "jane@example.com"}

HTTP/1.1 201 Created
Location: /api/users/12345
Content-Type: application/json

{"id": 12345, "name": "Jane Doe", "email": "jane@example.com"}

When designing REST APIs, using 201 instead of 200 for resource creation makes your API semantically correct. Clients can programmatically distinguish between "the action was performed" (200) and "a new resource was created" (201), which enables smarter client-side caching and UI behavior.

202 Accepted

The 202 Accepted status means the request has been accepted for processing, but the processing has not been completed. This is the correct response for asynchronous operations. The server is saying: "I got your request, it looks valid, and I will work on it, but I cannot give you the final result right now."

This code is common in systems that use background job queues. For example, if you submit a request to generate a large report, the server might respond with 202 and include a URL where you can poll for the result. Stripe uses 202 for webhook event processing. Video encoding services use 202 for upload requests that trigger transcoding pipelines.

204 No Content

The 204 No Content status means the request succeeded but there is no content to return in the response body. This is the standard response for successful DELETE requests when the server does not want to return the deleted resource. It is also used for PUT requests where the server has processed the update but does not need to return the updated resource.

The key distinction from 200 is that a 204 response must not include a response body. Browsers that receive a 204 from a form submission will not navigate away from the current page, which makes it useful for "save" actions that should keep the user on the same page.

206 Partial Content

The 206 Partial Content status indicates that the server is delivering only part of the resource. This happens when the client sends a Range header to request a specific byte range of a large file. Video streaming, audio playback, and resume-capable downloads all rely on 206 responses.

GET /video/tutorial.mp4 HTTP/1.1
Range: bytes=1048576-2097151

HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/52428800
Content-Length: 1048576
Content-Type: video/mp4

When you see a video player loading on a webpage, it is typically making multiple requests with Range headers, and the server responds with a series of 206 responses. This allows the player to start playback immediately without downloading the entire file. If a download is interrupted and resumed, the client sends a Range header starting from where it left off, and the server responds with 206 to deliver just the remaining portion.

3xx Redirection Responses

The 3xx class tells the client that it needs to take additional action to complete the request. Usually, this means the requested resource is available at a different URL. The distinction between different 3xx codes is critically important for SEO, caching, and bookmarking behavior.

301 Moved Permanently

The 301 status indicates that the requested resource has been permanently moved to a new URL. The response includes a Location header with the new URL. Browsers and search engines should update their records to use the new URL for all future requests. This is the single most important redirect code for SEO.

When you migrate a website to a new domain, restructure your URL paths, or switch from HTTP to HTTPS, 301 redirects tell search engines to transfer the ranking value (link equity) from the old URLs to the new ones. Without 301 redirects during a migration, you can lose years of accumulated search rankings overnight.

Real-world scenario

Your company rebrands from oldname.com to newname.com. Every page on the old domain should return a 301 redirect to the corresponding page on the new domain. For example, oldname.com/products/widget should 301 redirect to newname.com/products/widget. Google will process these redirects and eventually update its index to show the new URLs, carrying over the search rankings from the old domain.

Common mistake: Using 302 redirects when you mean 301. A 302 is temporary, so search engines will keep the old URL in their index. If your move is permanent, always use 301. I have seen sites lose significant organic traffic because someone configured 302 redirects instead of 301s during a domain migration.

302 Found (Temporary Redirect)

The 302 status indicates a temporary redirect. The resource is temporarily available at a different URL, but the client should continue to use the original URL for future requests. Browsers follow the redirect but do not update bookmarks. Search engines do not transfer ranking value to the new URL because they expect the original URL to become active again.

Legitimate uses for 302 include A/B testing (sending some users to a variant page temporarily), maintenance pages (redirecting to a "site under maintenance" page), and geolocation-based routing (redirecting users to their regional version temporarily).

303 See Other

The 303 status tells the client to redirect to a different URL using a GET request, regardless of what method was used in the original request. This is the correct redirect to use after a POST request. The classic pattern is POST/Redirect/GET (PRG): the client submits a form via POST, the server processes it and responds with 303, and the browser follows the redirect with a GET request to display the result page. This prevents the "resubmit form" dialog that appears when a user refreshes a page that was loaded via POST.

304 Not Modified

The 304 status is the backbone of HTTP caching. When a client has a cached version of a resource, it can send a conditional request with an If-Modified-Since or If-None-Match header. If the resource has not changed since the cached version, the server responds with 304 and an empty body, telling the client to use its cached copy. This saves bandwidth because the server does not need to retransmit the resource.

GET /styles/main.css HTTP/1.1
If-None-Match: "abc123"

HTTP/1.1 304 Not Modified
ETag: "abc123"
Cache-Control: max-age=3600

Seeing a high percentage of 304 responses in your server logs is generally a good sign. It means your caching strategy is working effectively. Conversely, if you never see 304s, your caching headers might be misconfigured, and you could be wasting bandwidth serving unchanged resources repeatedly.

307 Temporary Redirect

The 307 status is a strict temporary redirect that guarantees the request method will not change. Unlike 302, which historically allowed browsers to change the method from POST to GET (and most browsers did), 307 explicitly requires the client to use the same method for the redirected request. If the original request was a POST with a body, the redirect must also be a POST with the same body.

308 Permanent Redirect

The 308 status is the strict version of 301, guaranteeing that the request method will not change. It was introduced to address the same ambiguity that 307 addressed for 302. In practice, 301 and 308 behave identically for GET requests. The difference only matters for non-GET requests (like POST) where method preservation is important.

4xx Client Error Responses

The 4xx class tells the client that their request has a problem. The fault is on the client side: a malformed request, missing authentication, insufficient permissions, or a request for a resource that does not exist. These are the codes you see most frequently during development, and each one points to a specific category of client-side error.

400 Bad Request

The 400 status is the generic client error response. It indicates that the server could not process the request because of something the client did wrong: malformed syntax, invalid request parameters, deceptive routing, or a body that does not match the declared Content-Type. This is the catch-all for client errors that do not fit a more specific 4xx code.

In API development, 400 is the response for invalid input. If a client sends a JSON body with a missing required field, a string where a number is expected, or a date in the wrong format, the server should respond with 400 and a clear error message explaining what is wrong.

POST /api/orders HTTP/1.1
Content-Type: application/json

{"product_id": "abc", "quantity": -5}

HTTP/1.1 400 Bad Request
Content-Type: application/json

{
    "error": "validation_error",
    "details": [
        {"field": "product_id", "message": "Must be a numeric ID"},
        {"field": "quantity", "message": "Must be a positive integer"}
    ]
}

Debugging tip: When you get a 400 error from an API, read the response body carefully. Well-designed APIs include specific validation errors that tell you exactly which field is wrong and why. If the response body is empty or unhelpful, check the Content-Type header you are sending. A surprisingly common cause of 400 errors is sending JSON with a Content-Type: application/x-www-form-urlencoded header, or vice versa.

401 Unauthorized

The 401 status means the request requires authentication, and either no credentials were provided or the provided credentials are invalid. The name is somewhat misleading. It should really be called "Unauthenticated" because it is about identity (who you are), not permissions (what you are allowed to do). The 403 code handles the permissions case.

A 401 response should include a WWW-Authenticate header that tells the client what authentication scheme the server expects (Basic, Bearer, etc.). When a browser receives a 401 with a WWW-Authenticate: Basic header, it displays the username/password dialog box.

In modern web applications, 401 typically means the user's session has expired, their JWT token is invalid or expired, or they are trying to access an API endpoint without including an authorization header. The correct client behavior is to redirect the user to a login page or refresh the authentication token.

403 Forbidden

The 403 status means the server understood the request and the client is authenticated, but the client does not have permission to access the requested resource. The distinction from 401 is important: with 401, sending valid credentials might fix the problem. With 403, re-authenticating will not help because the server has already identified who you are and determined that you are not allowed.

Common causes of 403 include trying to access an admin-only resource with a regular user account, IP-based access restrictions that block your address, file system permissions that prevent the web server from reading a file, and web application firewalls that have blocked your request based on its content.

404 Not Found

The 404 status is the most recognizable HTTP status code, even among people who do not work in technology. It means the server could not find the requested resource. The URL might be mistyped, the resource might have been deleted, or the resource might never have existed at that location.

For SEO, 404 errors on pages that used to exist (and might have incoming links) should be addressed with 301 redirects to the most relevant replacement page. Persistent 404 errors waste your crawl budget, as search engines will keep trying to access URLs they have in their index. Google Search Console reports 404 errors, and I recommend checking this report monthly.

Custom 404 pages are a standard practice. Instead of showing the default server error page, a well-designed 404 page includes your site navigation, a search box, and links to popular pages. This keeps users on your site when they hit a broken link instead of bouncing back to search results.

405 Method Not Allowed

The 405 status means the request method (GET, POST, PUT, DELETE, etc.) is not supported for the requested resource. The response must include an Allow header listing the methods that are supported. For example, if you send a DELETE request to a read-only resource, the server should respond with 405 and an Allow: GET, HEAD header.

408 Request Timeout

The 408 status means the server timed out waiting for the client to finish sending the request. This is not about the server taking too long to process. It is about the client taking too long to transmit. Slow network connections, large file uploads over unstable connections, and clients that open connections but do not send data can trigger 408 responses.

409 Conflict

The 409 status indicates that the request conflicts with the current state of the server. The most common scenario is trying to create a resource that already exists (for example, registering a username that is already taken) or making a modification that violates a business rule. This code is also used in version control systems and collaborative editing applications when two clients try to modify the same resource simultaneously.

PUT /api/users/email HTTP/1.1
Content-Type: application/json

{"email": "taken@example.com"}

HTTP/1.1 409 Conflict
Content-Type: application/json

{"error": "conflict", "message": "This email address is already registered"}

410 Gone

The 410 status is like a permanent 404. It means the resource used to exist at this URL but has been permanently removed, and the server does not know a forwarding address. Unlike 404, which leaves open the possibility that the resource might appear in the future, 410 explicitly tells clients and search engines that this resource is gone for good and will not be coming back.

For SEO, 410 is stronger than 404 as a signal to search engines to remove a URL from their index. If you intentionally delete content and want Google to drop it from search results quickly, returning 410 is more effective than 404.

413 Content Too Large

The 413 status (previously called "Request Entity Too Large") means the request body exceeds the server's configured maximum size. Web servers like Nginx have a client_max_body_size directive that limits upload sizes. If a client tries to upload a 100 MB file to a server configured with a 10 MB limit, the server responds with 413.

This is one of the most common errors in file upload implementations. The fix is either to increase the server's upload limit or to implement chunked uploads on the client side that break large files into smaller pieces.

415 Unsupported Media Type

The 415 status means the server refuses to accept the request because the Content-Type of the request body is not supported. If an API endpoint expects JSON and you send XML, or if a file upload endpoint expects images and you send a PDF, the server should respond with 415.

422 Unprocessable Entity

The 422 status (originally from WebDAV but widely adopted in REST APIs) means the server understands the content type and the syntax is correct, but it cannot process the contained instructions. This is semantically different from 400: with 400, the request itself is malformed. With 422, the request is well-formed but contains logical errors.

For example, if you send a valid JSON body to create a user, but the email address fails validation rules (like a corporate policy that only allows company domain emails), that is a 422. The JSON is valid, the fields are present, but the data does not pass business logic validation. Many frameworks like Ruby on Rails use 422 by default for validation failures.

429 Too Many Requests

The 429 status means the client has sent too many requests in a given time period (rate limiting). The response should include a Retry-After header telling the client how long to wait before making another request. This code is essential for API protection, preventing abuse, and ensuring fair usage of shared resources.

HTTP/1.1 429 Too Many Requests
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1711360260

When building API clients, always implement exponential backoff when you receive a 429 response. Start by waiting the duration specified in Retry-After, then double the wait time for each subsequent 429. This prevents your client from hammering the server when it is already under load. 5xx Server Error Responses

The 5xx class indicates that the server has recognized that it has made an error or is incapable of performing the request. These are the codes that wake developers up at 3 AM. Unlike 4xx errors where the client is at fault, 5xx errors mean something on the server side has gone wrong and needs attention.

500 Internal Server Error

The 500 status is the generic server error response. It means something went wrong on the server, but the server cannot be more specific about what the problem is. Unhandled exceptions, null pointer errors, database connection failures, configuration errors, and countless other server-side issues can produce a 500 response.

When you encounter a 500 error in production, the response body typically contains a generic error page rather than the actual error details (which could expose sensitive information about your server configuration). The real debugging happens in server logs. Check your application logs, web server error logs (e.g., /var/log/nginx/error.log), and application performance monitoring tools for the stack trace.

Debugging tip: If you are seeing intermittent 500 errors (sometimes the request works, sometimes it does not), the most common causes are database connection pool exhaustion, race conditions under concurrent load, and memory limits being hit by certain types of requests. Check your server's memory usage, database connection count, and error log timestamps to correlate the 500s with resource bottlenecks.

502 Bad Gateway

The 502 status means that a server acting as a gateway or proxy received an invalid response from an upstream server. In modern web architecture, this usually means your reverse proxy (Nginx, HAProxy, or a cloud load balancer) tried to forward the request to your application server, but the application server returned something invalid or crashed before responding.

The most common causes of 502 errors are application servers that have crashed or are restarting, upstream services that are down, timeout mismatches between the proxy and the application server, and application servers that return malformed HTTP responses. In a Docker or Kubernetes environment, 502 errors during deployments usually mean the new container is not ready to accept connections yet.

503 Service Unavailable

The 503 status means the server is temporarily unable to handle the request due to maintenance or overload. Unlike 500, which suggests something is broken, 503 suggests the situation is temporary. The response should include a Retry-After header indicating when the client should try again.

Planned maintenance windows should return 503 with a Retry-After header. This tells search engine crawlers to come back later rather than removing the page from their index. If you return 500 during maintenance, search engines might interpret it as the page being broken and temporarily reduce its ranking.

504 Gateway Timeout

The 504 status means a server acting as a gateway or proxy did not receive a timely response from an upstream server. This is the timeout version of 502. Instead of getting an invalid response, the proxy got no response at all within its configured timeout period.

In practice, 504 errors often indicate that a database query is taking too long, an external API call is hanging, or the application server is stuck in a long-running operation that exceeds the proxy's timeout. The fix usually involves optimizing the slow operation, increasing timeout values (as a temporary measure), or implementing asynchronous processing for long-running operations.

# Nginx proxy timeout configuration
location /api/ {
    proxy_pass http://backend;
    proxy_connect_timeout 60s;
    proxy_send_timeout 60s;
    proxy_read_timeout 120s;  # Increase for slow endpoints
}

505 HTTP Version Not Supported

The 505 status means the server does not support the HTTP protocol version used in the request. This is rare in practice because most servers support HTTP/1.0, HTTP/1.1, and HTTP/2. You might encounter it with very old or misconfigured servers, or with clients that attempt to use an unsupported protocol version.

507 Insufficient Storage (WebDAV)

The 507 status is a WebDAV extension that means the server cannot store the representation needed to complete the request. In practice, this usually means the server's disk is full. While it is a WebDAV code, some storage APIs and file hosting services return 507 when they run out of allocated space.

508 Loop Detected (WebDAV)

The 508 status indicates that the server detected an infinite loop while processing a request with Depth: infinity. This is specific to WebDAV operations that traverse directory structures. It prevents the server from entering an infinite loop when symbolic links or directory references create circular paths.

511 Network Authentication Required

The 511 status indicates that the client needs to authenticate to gain network access. This is the status code returned by captive portals, the Wi-Fi login pages you see at hotels, airports, and coffee shops. When you connect to a public Wi-Fi network that requires you to accept terms of service or enter a password before granting internet access, the captive portal intercepts your HTTP request and responds with 511.

Debugging Status Codes in Practice

Understanding what each status code means is only half the battle. The other half is knowing how to investigate when you see an unexpected code. Here is my systematic approach to debugging HTTP issues, refined through years of production incident response.

Step 1: Reproduce and Capture

Before debugging, you need to see the full request and response. Browser DevTools (Network tab) shows you everything for browser requests. For API debugging, I use tools that let me inspect the complete HTTP conversation including all headers. Our HTTP Status Checker provides a quick way to check response codes and headers for any URL.

# Using curl to see full request/response headers
curl -v https://example.com/api/users

# Using curl to see just the response headers
curl -I https://example.com/api/users

# Following redirects and showing each hop
curl -v -L https://example.com/old-page

Step 2: Check the Response Headers

Response headers contain critical debugging information that the status code alone does not provide. Check the Content-Type header to ensure the response format matches your expectation. Check the Location header on redirect responses. Check Retry-After on 429 and 503 responses. Check WWW-Authenticate on 401 responses to understand the expected authentication scheme.

Step 3: Read the Response Body

Well-designed APIs include detailed error information in the response body for 4xx and 5xx errors. Do not assume the status code tells you everything. A 400 response from a Stripe API endpoint includes a JSON body with the specific validation error, the field that caused the error, and a machine-readable error code. Always read the body.

Step 4: Check Server Logs

For 5xx errors, the server logs are your primary source of truth. The application log will contain the stack trace that caused the error. The web server access log will show the exact request that triggered it. The web server error log will show proxy-level errors for 502 and 504 codes. If you are running in a containerized environment, check both the container logs and the orchestrator logs.

Step 5: Compare Working and Broken Requests

If a request used to work and now fails, compare a captured working request with the failing one. Look for differences in headers, authentication tokens, request body format, URL encoding, and query parameters. Version differences in APIs (v1 vs v2 endpoints) are a frequent culprit when requests suddenly start failing.

Status Codes in REST API Design

If you are designing a REST API, choosing the right status codes is part of creating a good developer experience. Here are the conventions I follow, based on building and consuming dozens of production APIs.

Operation Success Code Common Error Codes
GET (retrieve)200401, 403, 404
POST (create)201400, 401, 409, 422
PUT (update)200 or 204400, 401, 404, 409, 422
PATCH (partial update)200400, 401, 404, 422
DELETE (remove)204401, 403, 404
POST (async action)202400, 401, 429

One principle I advocate strongly: never embed errors inside 200 responses. I have worked with APIs that return 200 OK with a body like {"success": false, "error": "Not found"}. This breaks every HTTP client, monitoring tool, and caching layer that relies on status codes for correct behavior. If something went wrong, use a proper error status code. Reserve 200 for actual success.

When you are building or consuming APIs, format and inspect responses using the API Response Formatter tool. Clean formatting makes it much easier to spot issues in the response structure.

SEO Impact of Status Codes

Status codes have a direct impact on how search engines index and rank your pages. Understanding this relationship is essential for anyone managing a website's organic search presence.

Redirects and Link Equity

When a page with incoming links returns a 301 redirect, Google passes most of the link equity to the target URL. The process is not instant. It can take weeks for Google to fully process a redirect chain and update its index. Multiple chained redirects (A redirects to B, which redirects to C) lose a small amount of equity at each hop. Keep redirect chains to a maximum of two hops, and ideally just one.

The 302 redirect does not pass link equity because Google interprets it as temporary. If you accidentally use 302 instead of 301 for a permanent move, Google will keep the old URL in its index and the new URL will not benefit from the old page's backlinks.

Soft 404s

A soft 404 is a page that returns a 200 status code but displays content that suggests it should be a 404 (empty pages, "page not found" text, thin content). Google detects soft 404s and treats them similarly to real 404s, but the mixed signal can confuse their crawling and indexing. Always return the correct status code: 404 for pages that do not exist, 200 for pages with real content.

503 During Maintenance

During planned maintenance, return 503 with a Retry-After header. Google will pause crawling and come back after the specified period. If you return 500 during maintenance, Google might interpret it as a persistent problem and temporarily reduce your rankings. If you return 200 with a maintenance page, Google might index your maintenance page as the actual content.

Monitoring and Alerting on Status Codes

In a production environment, monitoring HTTP status codes across your infrastructure provides early warning of problems before they become visible to users. Here is the monitoring strategy I implement on every system I manage.

What to Monitor

Track the rate of each status code category (2xx, 3xx, 4xx, 5xx) over time. A sudden spike in 5xx errors indicates a server-side problem. A gradual increase in 4xx errors might indicate a broken client, a misconfigured deployment, or a crawler hitting nonexistent URLs. A decrease in 2xx responses paired with an increase in any error code indicates a degradation in service.

Alert Thresholds

Set alerting thresholds based on your normal baseline. If your application normally has a 0.1% error rate (5xx responses as a percentage of total responses), alert when it exceeds 1% for more than 5 minutes. For 4xx errors, alert on sudden percentage increases rather than absolute counts, since 404 errors from web crawlers are normal background noise.

The specific codes to create dedicated alerts for are 500 (application errors that need investigation), 502 and 504 (proxy/upstream issues that indicate infrastructure problems), 503 (service overload that might require scaling), and 429 (rate limiting that might indicate a misconfiguration or an attack).

Log Analysis

Every HTTP request should be logged with at minimum the timestamp, client IP, request method, URL, status code, response time, and response size. This log data enables you to correlate status code anomalies with specific endpoints, client IPs, time periods, and deployment events. Tools like the ELK stack (Elasticsearch, Logstash, Kibana), Grafana with Loki, and Datadog provide dashboards for visualizing this data.

# Example Nginx log analysis: top 5xx URLs in the last hour
awk '$9 ~ /^5/ {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# Count status codes by category
awk '{print substr($9,1,1)"xx"}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

The combination of real-time monitoring, threshold-based alerting, and post-incident log analysis ensures that status code anomalies are caught early and investigated thoroughly. Every production outage I have investigated started with an abnormal pattern in HTTP status codes, and the teams that monitor these codes recover faster than those that wait for users to report problems.
