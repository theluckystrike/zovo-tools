What Cookies Actually Are

I have been building Chrome extensions for years, and one thing I notice consistently is that most people have a vague idea of what cookies are without understanding the mechanics. That vagueness leads to bad decisions about privacy settings, broken login sessions, and confusion about consent banners. So before I walk through the practical steps for managing cookies, I want to lay down what is actually happening under the hood.

A cookie is a small text file that a web server sends to your browser. Your browser stores it and sends it back with every subsequent request to that same server. That is the entire mechanism. The server says "remember this," and your browser remembers it. Cookies were invented by Lou Montulli at Netscape in 1994 to solve a fundamental problem with HTTP: the protocol is stateless. Without cookies, the server has no way to know whether two requests come from the same person. Every page load would be a blank slate.

There are several types of cookies, and understanding the distinctions matters for both privacy and debugging.

First-Party Cookies

First-party cookies are set by the domain you are currently visiting. When you log into your bank at example-bank.com, that server sets a cookie on the example-bank.com domain containing a session token. Your browser sends that cookie back with every request to example-bank.com, which is how the server knows you are still logged in. First-party cookies are essential for virtually every modern website. Without them, you could not stay logged in, maintain a shopping cart, or save preferences like language and theme.

Third-Party Cookies

Third-party cookies are set by domains other than the one in your address bar. When you visit a news site that loads an ad from ad-network.com, that ad network can set a cookie on your browser under the ad-network.com domain. When you later visit a different site that also loads ads from ad-network.com, the same cookie is sent along, allowing the ad network to track your browsing across both sites. This cross-site tracking is the primary privacy concern with cookies and the reason browsers have been systematically restricting third-party cookies.

Session Cookies vs. Persistent Cookies

Session cookies have no explicit expiration date. They exist only in memory and are deleted when you close your browser. Persistent cookies have an expiration date set by the server, which can range from minutes to years. A "remember me" login cookie is typically persistent with a long expiration. A CSRF token cookie might be session-only.

Secure, HttpOnly, and SameSite Flags

Beyond the basic name-value pair, cookies have several important attributes that control their behavior.

Understanding these attributes is not just academic. When I am debugging authentication failures or investigating why a site is not working correctly after clearing cookies, the first thing I check is whether the cookie flags match what the application expects. A missing SameSite attribute or an incorrectly scoped Domain value causes real, frustrating breakage.

Viewing Cookies in Chrome DevTools

The most detailed way to inspect cookies is through Chrome's Developer Tools. DevTools gives you a complete view of every cookie associated with the current page, including cookies from third-party domains that loaded resources on the page.

Opening the Application Tab

Press F12 or Ctrl+Shift+I on Windows and Linux, or Cmd+Option+I on macOS, to open DevTools. Navigate to the Application tab at the top of the DevTools panel. If you do not see it, click the double-arrow overflow icon to find it in the dropdown menu. The Application tab is sometimes hidden when DevTools is in a narrow configuration.

In the left sidebar of the Application tab, you will see a Storage section. Expand the Cookies entry, and you will see a list of domains that have set cookies on the current page. Click any domain to see its cookies in the main panel.

Understanding the Cookie Table

The cookie table displays each cookie as a row with the following columns.

ColumnWhat It Shows
NameThe cookie identifier. Common names include session_id, _ga (Google Analytics), csrf_token, and __cfduid (Cloudflare).
ValueThe data stored in the cookie. This might be a session token, a user ID, an encoded JSON object, or a tracking identifier.
DomainThe domain scope. A cookie with domain .example.com is sent to all subdomains. A cookie with www.example.com is only sent to that exact subdomain.
PathThe URL path scope. A cookie with path / is sent with every request to the domain. A cookie with path /account is only sent for URLs under /account.
Expires / Max-AgeWhen the cookie will be deleted. "Session" means it will be deleted when the browser closes.
SizeThe total size of the cookie name plus value in bytes. Individual cookies are limited to about 4 KB.
HttpOnlyWhether JavaScript can access the cookie. A checkmark means it is HttpOnly and protected from script access.
SecureWhether the cookie is restricted to HTTPS. A checkmark means it will not be sent over plain HTTP.
SameSiteThe cross-site request policy. Shows Strict, Lax, None, or blank (unset, defaults to Lax in Chrome).
PriorityChrome-specific attribute. Low, Medium, or High. Affects which cookies are evicted first when the per-domain cookie limit is reached.

You can sort the table by clicking any column header. I usually sort by Domain to group first-party and third-party cookies, or by Expires to identify persistent tracking cookies.

Editing Cookies in DevTools

Double-click any cell in the cookie table to edit its value directly. This is useful for testing how your application handles modified cookie data. For example, you can change a session token to test session validation, modify a preference cookie to test different user settings, or alter an A/B testing cookie to switch between experiment groups.

After editing a cookie value, refresh the page to see how the application responds to the new value. Be careful with HttpOnly cookies on sites that validate server-side. The server may reject the modified value and force a logout.

Tip. Right-click the cookie table header row to toggle which columns are visible. By default, the Priority and Partition Key columns are hidden. Enable them if you are debugging partitioned cookies or investigating cookie eviction issues.

Filtering and Searching

The filter box at the top of the cookie table lets you search by cookie name or value. Type any string and the table instantly filters to matching cookies. This is invaluable on pages that set dozens of cookies. For example, typing _ga will show all Google Analytics cookies, while typing session will reveal session-related cookies from various services.

You can also use the "Has blocked cookies" checkbox filter to see only cookies that Chrome has blocked due to SameSite policies or third-party cookie restrictions.

Deleting Cookies for a Single Site

This is one of the most common tasks, and there are multiple ways to accomplish it depending on how targeted you need to be.

Method 1. DevTools Application Tab

This gives you the most granular control. Open DevTools, go to the Application tab, expand Cookies, and click the domain. To delete individual cookies, select them and press the Delete key or click the clear icon (the circle with a line through it) in the toolbar above the table. To delete all cookies for a specific domain, right-click the domain name in the left sidebar and select "Clear."

I use this method when I need to delete specific cookies while keeping others intact. For example, when debugging a login issue, I might delete only the session cookie while keeping preference cookies so I do not lose my theme and language settings.

Method 2. The Address Bar Lock Icon

Click the lock icon (or the tune/settings icon in newer Chrome versions) to the left of the URL in the address bar. Click "Cookies" or "Site settings." You will see a dialog showing all cookies and site data for the current domain. You can expand each domain, select individual cookies, and click "Remove" to delete them. Click "Remove All" to clear everything for the site.

This method is more accessible for non-developers since it does not require opening DevTools. However, it provides less detail about each cookie compared to the Application tab.

Method 3. Chrome Settings

Navigate to chrome://settings/cookies or go to Settings, then Privacy and Security, then Cookies and other site data, then "See all cookies and site data." This page shows every domain that has stored cookies in your browser. Use the search box to find a specific domain, then click the trash icon to delete all cookies and data for that site.

Chrome Settings Path:
Settings → Privacy and Security → Cookies and other site data → See all cookies and site data

This method is useful when you want to clear cookies for a site you are not currently visiting. It also shows the total number of cookies and amount of data stored per domain, which helps identify sites that store excessive data.

Method 4. Clear Browsing Data

Press Ctrl+Shift+Delete (or Cmd+Shift+Delete on macOS) to open the Clear Browsing Data dialog. The Basic tab lets you clear all cookies for a time range (last hour, last 24 hours, last 7 days, last 4 weeks, or all time). The Advanced tab gives you separate checkboxes for cookies, cached images, and other data types.

Be aware that clearing all cookies will log you out of every website. I recommend using the site-specific methods above unless you genuinely want a fresh start. Over the years I have seen too many people clear all cookies as a troubleshooting step when the problem only required removing cookies from a single domain.

Tip. If you frequently need to clear cookies for a specific site during development, create a Chrome bookmark with the JavaScript bookmarklet javascript:void(document.cookie.split(';').forEach(c=>document.cookie=c.trim().split('=')[0]+'=;expires=Thu, 01 Jan 1970 00:00:00 GMT;path=/')) to instantly clear non-HttpOnly cookies for the current domain.

Chrome's Cookie Settings

Chrome provides several built-in controls for managing how cookies are handled across all websites. These settings live at chrome://settings/cookies and affect your default cookie policy.

General Cookie Behavior

Chrome offers four main cookie modes.

  • "Allow all cookies" permits first-party and third-party cookies from all domains. This is the least private but most compatible setting.
  • "Block third-party cookies in Incognito" allows third-party cookies in regular browsing but blocks them in Incognito mode. This was the default for a long time.
  • "Block third-party cookies" prevents any domain other than the one in your address bar from setting cookies. This breaks some legitimate features like embedded payment forms, federated login (Sign in with Google), and embedded content players.
  • "Block all cookies" prevents any cookies from being set. This effectively breaks most of the modern web and is not practical for daily use.

I run with "Block third-party cookies" as my default and add exceptions for the handful of sites that genuinely need them. This provides a good privacy baseline without the constant breakage of blocking all cookies.

Site-Specific Exceptions

Below the general setting, Chrome offers three exception lists.

  • "Sites that can always use cookies" is a whitelist. Cookies from these domains are always accepted regardless of your general setting.
  • "Sites that can never use cookies" is a blacklist. These domains can never set cookies, even if your general setting allows them.
  • "Sites that always clear cookies when windows are closed" auto-deletes cookies from these domains whenever you close all Chrome windows. This is useful for sites you want to use but do not want tracking you long-term.

To add a site to any of these lists, click the "Add" button and enter the domain pattern. You can use [*.]example.com to match all subdomains. I keep my bank and email domains in the "always allow" list to prevent accidental clearing, and I put known tracking domains in the "never allow" list.

Clear on Exit

The "Clear cookies and site data when you close all windows" toggle deletes all cookies every time you fully close Chrome. This is a nuclear option that provides strong privacy at the cost of being logged out of everything each session. If you want this behavior for only specific sites rather than all of them, use the site-specific "always clear when windows are closed" list instead.

Cookie Exception Pattern Examples:
[*.]example.com → matches example.com and all subdomains
https://specific.example.com → matches only that exact origin
http://insecure.example.com → matches only HTTP version

The Cookie Law and Consent Banners Explained

If you have used the internet at any point in the last decade, you have seen cookie consent banners. They range from a simple "We use cookies" notification with an OK button to sprawling consent management platforms with toggles for dozens of cookie categories. Here is what is actually going on.

The EU ePrivacy Directive

The original "cookie law" is the EU ePrivacy Directive (2002/58/EC, amended in 2009). It requires websites to obtain informed consent before storing non-essential cookies on a user's device. "Non-essential" means anything beyond what is strictly necessary for the service the user requested. Session cookies for login are essential. Analytics and advertising cookies are not.

The directive applies to any website that serves users in the EU, regardless of where the website is based. This is why American websites that have EU traffic show consent banners.

GDPR and Cookie Consent

The General Data Protection Regulation (GDPR), which took effect in 2018, raised the stakes significantly. GDPR governs the processing of personal data, and cookie identifiers qualify as personal data when they can be used to identify individuals. This means that the consent requirements for tracking cookies are backed by GDPR's enforcement mechanism, which includes fines of up to 4% of global annual revenue.

Under GDPR, valid consent must be freely given, specific, informed, and unambiguous. Pre-checked boxes do not count. "Cookie walls" that block content unless you accept all cookies are considered coercive in most EU jurisdictions. The user must be able to reject non-essential cookies as easily as they accept them.

What the Categories Mean

Most consent management platforms organize cookies into categories. Here is what they typically mean in practice.

  • "Strictly Necessary" covers cookies required for basic site functionality like login sessions, shopping carts, load balancers, and CSRF tokens. These do not require consent.
  • "Performance" or "Analytics" covers cookies that collect usage data, page view counts, and user behavior patterns. Google Analytics, Hotjar, and similar tools fall here.
  • "Functional" covers cookies that remember user preferences like language, theme, font size, and region. Some frameworks categorize these as strictly necessary; others require consent.
  • "Targeting" or "Advertising" covers cookies used for ad personalization, retargeting, conversion tracking, and cross-site profiling. These are the most privacy-invasive category.

When I encounter a consent banner, I typically accept only Strictly Necessary and Functional cookies and reject everything else. On sites I visit regularly, I will enable Analytics if I know the site uses it to genuinely improve the product rather than for surveillance.

Consent Banners in Practice

The quality of consent implementations varies enormously. Some sites use compliant consent management platforms like Cookiebot, OneTrust, or Osano that genuinely respect your choices and block scripts until consent is given. Others use what I call "theater consent," where the banner appears but all cookies are set regardless of whether you click Accept or not. Enforcement has been inconsistent, though regulators have been issuing more fines in recent years, particularly in France (CNIL) and Ireland (DPC).

From a practical standpoint, if you want to minimize tracking regardless of consent banners, blocking third-party cookies in Chrome settings and using an extension like Cookie Manager Pro to periodically audit and clean cookies is more reliable than trusting every consent banner to work correctly.

Using Incognito Mode for Cookie Isolation

Incognito mode is one of the most misunderstood features in Chrome. I want to be precise about what it does and does not do for cookie management.

What Incognito Actually Does

When you open an Incognito window (Ctrl+Shift+N or Cmd+Shift+N), Chrome creates an isolated browsing session with a separate cookie jar. Websites can still set and read cookies within that session. The isolation comes from two properties. First, the Incognito cookie jar starts empty and does not have access to cookies from your regular browsing session. Second, when you close all Incognito windows, every cookie from that session is permanently deleted.

This means Incognito mode is effectively equivalent to a session-only cookie policy. Cookies work normally while you are browsing, but nothing persists. You will need to log in to every site each time you open a new Incognito session.

What Incognito Does Not Do

Incognito does not make you anonymous. Your ISP can still see your traffic. Websites can still identify you by IP address, browser fingerprint, or if you log into your account. Employers monitoring the network can still see your requests. Incognito prevents other users of the same computer from seeing your browsing history and prevents cookies from persisting, but it provides no network-level privacy.

Incognito also does not prevent all forms of tracking within a session. If you visit multiple sites in the same Incognito window, third-party cookies can still track you across those sites during that session (unless you have third-party cookies blocked). The tracking data is deleted when you close the window, but the tracking itself still occurs.

Practical Uses for Cookie Isolation

I use Incognito mode for several cookie-related purposes.

  • Testing websites without my existing cookies interfering. This is the fastest way to see what a new visitor experiences.
  • Logging into a different account on a service where I already have a session in my regular browser. Rather than signing out and back in, I open Incognito and log in with the other account.
  • Browsing sites I do not want tracking me long-term. Because all cookies are deleted when I close the window, there is no persistent tracking cookie left behind.
  • Debugging cookie-related issues. If a website is misbehaving and I suspect a corrupted or stale cookie is the cause, opening it in Incognito immediately tells me whether cookies are the problem. If the site works fine in Incognito, a cookie in my regular session is likely the issue.

Tip. You can open a link directly in Incognito by right-clicking it and selecting "Open link in incognito window." This is faster than opening a new Incognito window and navigating there manually.

Chrome Profiles as an Alternative

For longer-running isolation, Chrome profiles are more practical than Incognito. Each Chrome profile has its own completely separate set of cookies, extensions, bookmarks, and settings. I maintain separate profiles for personal browsing, work, and development testing. This gives me persistent isolation without the inconvenience of losing everything when I close a window.

Cookies and Privacy

Cookies are the oldest and most visible form of web tracking, but they exist within a broader ecosystem of privacy-relevant technologies. Understanding that context helps you make better decisions about which cookies to keep, which to block, and what other measures to take.

Cross-Site Tracking

The classic tracking mechanism works like this. An advertising network places code (typically an image pixel or JavaScript snippet) on thousands of websites. Each time you visit any of those sites, the tracking code loads from the ad network's domain and sets a cookie with a unique identifier. Because the same cookie is sent back every time the ad network's code loads, the network builds a profile of which sites you visit, when, and how often. This profile is then used to serve targeted ads.

Google's own advertising cookie, the NID cookie on the .google.com domain, is one of the most widespread. Facebook's _fbp cookie performs a similar function for the Meta advertising network. These are third-party cookies when encountered on non-Google or non-Facebook sites.

The Third-Party Cookie Phase-Out

Google has been working on phasing out third-party cookies in Chrome for several years. The timeline has shifted multiple times, but the direction is clear. Safari and Firefox already block third-party cookies by default. Chrome's Privacy Sandbox initiative proposes replacement technologies like the Topics API (which shares broad interest categories instead of individual tracking data) and the Attribution Reporting API (which provides conversion measurement without cross-site identifiers).

As a practical matter, even before third-party cookies are fully removed from Chrome, blocking them in your Chrome settings today has minimal impact on most browsing. The sites that break are typically those using third-party login widgets or embedded payment processors, and you can add those to your exception list.

Beyond Cookies. Fingerprinting

As cookies become less viable for tracking, more sophisticated techniques have gained prevalence. Browser fingerprinting collects characteristics of your browser and device including screen resolution, installed fonts, WebGL renderer, canvas rendering patterns, audio context fingerprints, and dozens of other signals to create a unique identifier without storing anything on your device.

Unlike cookies, you cannot "clear" a fingerprint. It is derived from your system's characteristics, not from stored data. The best defenses are browsers with anti-fingerprinting features (Brave, Tor Browser) or extensions that randomize fingerprinting signals. This is worth understanding because people who diligently manage their cookies sometimes assume they are preventing tracking, when in reality fingerprinting provides an alternative identification mechanism.

Local Storage and IndexedDB

Cookies are not the only client-side storage mechanism. Modern websites also use localStorage (up to 5-10 MB of key-value data per domain), sessionStorage (similar but cleared when the tab closes), and IndexedDB (a full client-side database with essentially unlimited storage). Some tracking systems have migrated from cookies to these alternatives because they are less visible and not subject to the same third-party restrictions.

You can inspect and clear all of these in the Application tab of DevTools, just like cookies. I recommend periodically checking a site's localStorage and IndexedDB alongside its cookies to get a complete picture of what data it stores on your machine.

Developer Debugging with Cookies

For developers, cookies are a constant part of the debugging workflow. Authentication, session management, CSRF protection, and feature flags all depend on cookies, and when they go wrong, the symptoms can be confusing.

Debugging Authentication Failures

When a user reports being unexpectedly logged out, my debugging checklist starts with cookies.

  1. Check whether the session cookie is present. Open the Application tab and look for the session cookie (commonly named session, sid, PHPSESSID, connect.sid, or similar). If it is missing, the cookie was either deleted, expired, or never set.
  2. Check the cookie's expiration. If it is a session cookie (no explicit expiration), closing and reopening the browser will have deleted it. If it has a Max-Age, verify the value is reasonable.
  3. Check the Domain attribute. If the cookie's domain does not match the current domain (including subdomain rules), the browser will not send it. A cookie set for app.example.com will not be sent to www.example.com.
  4. Check the Secure flag. If the cookie has the Secure flag but the page loaded over HTTP (perhaps due to a misconfigured redirect), the browser will not send the cookie.
  5. Check SameSite. If the user arrived at the site via a cross-site redirect (from an email link, for example) and the cookie has SameSite=Strict, the cookie will not be sent on the initial navigation.
  6. Check the Network tab. Select the page request and look at the Cookie header in the Request Headers section. This shows exactly which cookies were sent to the server. Compare this to what you see in the Application tab.

CSRF Token Debugging

Cross-Site Request Forgery (CSRF) protection typically involves a cookie-to-header or cookie-to-form-field token comparison. The server sets a CSRF token in a cookie, the JavaScript on the page reads that cookie and includes the token in a custom header or form field, and the server verifies that they match.

Common CSRF debugging issues include the cookie being HttpOnly (so JavaScript cannot read it to send the header), the cookie domain not matching the request domain, or the cookie being blocked by SameSite restrictions on cross-origin form submissions. Check both the cookie and the request headers in the Network tab to see if the token is present and matching.

Testing with Modified Cookies

Developers frequently need to simulate different user states by modifying cookies. Here are patterns I use regularly.

  • Change a role indicator to test authorization. If your app stores a role hint in a cookie (the actual authorization check should be server-side), editing the cookie lets you see what a different role's UI looks like.
  • Set a feature flag cookie to enable or disable features without deploying code. Many feature flag systems check a cookie before falling back to the server-side flag value.
  • Modify the locale or language cookie to test internationalization without changing your browser settings.
  • Delete the A/B test assignment cookie to get re-assigned to a different experiment group.

Console Commands for Cookie Operations

When you need to script cookie operations, the browser console provides direct access.

// Read all non-HttpOnly cookies
document.cookie

// Set a new cookie
document.cookie = "test_flag=enabled; path=/; max-age=3600"

// Delete a cookie by setting expiration in the past
document.cookie = "test_flag=; path=/; expires=Thu, 01 Jan 1970 00:00:00 GMT"

// Parse cookies into an object
Object.fromEntries(document.cookie.split('; ').map(c => c.split('=')))

Remember that document.cookie cannot access HttpOnly cookies. For those, you need to use DevTools or an extension like Cookie Manager Pro that uses the Chrome cookies API to access all cookies regardless of HttpOnly status.

Network Tab Cookie Inspection

The Network tab provides a different perspective on cookies. Select any request and look at the Headers section. You will see two cookie-related areas. The "Cookie" request header shows every cookie that was sent to the server with that specific request. The "Set-Cookie" response header (under Response Headers) shows any new cookies the server is setting or updating.

This request-level view is essential when a cookie is present in the Application tab but not being sent with a specific request. The mismatch is usually caused by a path, domain, SameSite, or Secure flag restricting the cookie's scope.

Tip. In the Network tab, you can filter requests to show only those that set cookies. Click the filter box and type has-response-header:set-cookie to see only responses that include a Set-Cookie header. This is the fastest way to identify which server responses are creating or modifying cookies.

Cookie Size and Performance

Every cookie for a domain is sent with every HTTP request to that domain, including requests for images, stylesheets, and scripts. If a domain has 20 cookies totaling 3 KB, that adds 3 KB of overhead to every single request. On a page that loads 50 resources from the same domain, that is 150 KB of redundant cookie data.

This is why best practice for performance-sensitive applications is to keep cookies small, use a separate cookieless domain for static assets (like images and CSS), and store larger data in localStorage or IndexedDB instead of cookies.
