The Actual Math Behind Password Cracking: Why Length Beats Complexity

I spent years telling people to use "complex" passwords with uppercase, numbers, and symbols. Then I sat down and did the actual entropy calculations. The numbers tell a different story than conventional wisdom. This is that story, with every calculation shown.

By Michael Lip / March 25, 2026 / 25 min read

Entropy: The Single Number That Measures Password Strength

Password strength is not a feeling. It is a number, measured in bits of entropy. Entropy quantifies the size of the search space an attacker must exhaust to guarantee finding your password through brute force.

The formula is straightforward.

Entropy (bits) = log2(CL) = L * log2(C)

C is the size of the character set. L is the length of the password. Each bit of entropy doubles the number of possible combinations. A password with 40 bits of entropy has 2^40 = approximately 1.1 trillion possible combinations. A password with 80 bits has 2^80 = approximately 1.2 * 10^24 combinations.

Let me calculate the entropy per character for different character sets.

These numbers are the key to everything that follows. Adding symbols to your character set increases entropy by 0.62 bits per character (from 5.95 to 6.57). Adding one more character to your password's length adds the full entropy-per-character value. At the full ASCII set, that is 6.57 bits per additional character.

This is why length beats complexity. Making a password one character longer always adds more entropy than switching from alphanumeric to "alphanumeric plus symbols" on the same length password.

The Math That Proves Length Wins

Let me put specific numbers on this claim.

Password A: 8 characters, full ASCII (95 chars). Entropy = 8 * 6.57 = 52.6 bits. Combinations: 6.6 * 10^15 (6.6 quadrillion).

Password B: 16 characters, lowercase only (26 chars). Entropy = 16 * 4.70 = 75.2 bits. Combinations: 4.3 * 10^22 (43 sextillion).

Password B has 22.6 more bits of entropy than Password A. That means Password B has 2^22.6 = approximately 6.3 million times more possible combinations. The 16-character lowercase password is six million times harder to brute-force than the 8-character complex password.

And Password B is dramatically easier to type and remember. thunderhorsemaplecream versus kR7#mP2x.

The hash algorithm your password is stored with matters more than almost anything about the password itself.

Cloud-Scale Attacks

A well-funded attacker renting cloud GPUs can assemble significant cracking power. At current cloud GPU prices, renting 100 RTX A100 GPUs costs roughly $200/hour. This provides approximately 2 trillion MD5 hashes per second.

A nation-state with dedicated hardware could plausibly achieve 10-100 trillion MD5 hashes per second. Against password-specific hashing (bcrypt, Argon2), even this level of hardware is limited to thousands of hashes per second per GPU, making brute force against strong passwords infeasible.

Why "P@ssw0rd!" Is Terrible Despite Meeting Complexity Rules

The theoretical entropy of "P@ssw0rd!" based on character set analysis is 59.2 bits (9 characters from the 95-character ASCII set). But theoretical entropy assumes every character is chosen randomly and independently. "P@ssw0rd!" is not random. It is a predictable transformation of the word "password."

Attackers do not try every random combination first. They use rule-based attacks that apply common transformations to dictionary words.

  • Start with "password" (in every dictionary)
  • Capitalize first letter: "Password"
  • Replace a with @: "P@ssword"
  • Replace o with 0: "P@ssw0rd"
  • Append !: "P@ssw0rd!"

Hashcat's rule engine can apply these transformations to a dictionary of 10 million common passwords in seconds. The effective entropy of "P@ssw0rd!" is not 59.2 bits. It is closer to 20-25 bits because the transformation pattern is predictable. An attacker using a dictionary plus rules would crack it in minutes, not the millions of years the character-set entropy would suggest.

Contrast this with "correct horse battery staple" (the famous XKCD example). Four random words from a 7,776-word Diceware list. The entropy is 4 * log2(7776) = 4 * 12.9 = 51.7 bits. This is lower than the theoretical entropy of "P@ssw0rd!" but massively higher than its effective entropy. Because the words are chosen randomly (not based on a pattern), there are no shortcuts. The attacker must search the full 7,776^4 = 3.7 trillion combinations.

Theoretical entropy assumes random generation. Effective entropy accounts for how humans actually choose passwords. A password that looks complex but follows a predictable pattern has low effective entropy. A password that looks simple but was randomly generated has high effective entropy. Randomness is the key variable, not visual complexity.

Use actual dice or a cryptographically secure random generator.

What Happens to Your Password Server-Side

When you create an account and set a password, a well-built service does not store the password itself. It stores a hash of the password. When you log in, the service hashes the password you entered and compares it to the stored hash. If they match, you are authenticated. The original password is never stored or retrievable.

This means a database breach exposes hashes, not passwords. The attacker must "crack" each hash by finding an input that produces the same output. The difficulty of cracking depends entirely on which hash algorithm was used.

MD5 and SHA Family: Fast and Dangerous

MD5 and SHA-1/SHA-256 are general-purpose hash functions designed to be fast. Speed is exactly what you do not want for password storage. Fast hashing means fast cracking.

MD5 produces a 128-bit hash: 5f4dcc3b5aa765d61d8327deb882cf99 is the MD5 hash of "password." Any attacker with a basic lookup table cracks this instantly. Even without a lookup table, MD5's speed (164 billion hashes/second on one GPU) means short passwords are brute-forced in seconds.

SHA-256 is slower than MD5 but still far too fast for passwords at 22 billion hashes per second.

bcrypt: The Current Standard

bcrypt was published in 1999 by Niels Provos and David Mazieres. It was specifically designed for password hashing with three critical features.

Adjustable cost factor. The cost parameter determines how many iterations of the internal Blowfish cipher are performed. Each increment of the cost factor doubles the computation time. Cost 10 takes about 80ms. Cost 12 takes about 250ms. Cost 14 takes about 1 second. You can increase the cost as hardware gets faster, maintaining the same real-time delay.

Built-in salt. bcrypt generates a 128-bit random salt and embeds it in the output hash. The full bcrypt output looks like: $2b$12$LJ3m4ys3Lgzy/sPxFOKK3OUzHJC1uG.VwpBIcfhJGpOE5BFKX8cjO. The $2b$ identifies the algorithm version. $12$ is the cost factor. The next 22 characters are the salt. The remaining characters are the hash. Everything needed to verify the password is in this single string.

Constant-time comparison. The verification function compares hashes using constant-time comparison to prevent timing attacks, where an attacker could determine how many characters of a hash match based on the time the comparison takes.

scrypt: Adding Memory Hardness

scrypt, published in 2009 by Colin Percival, addressed a limitation of bcrypt: GPU parallelism. bcrypt's computation is CPU-bound but requires relatively little memory. GPUs have thousands of cores that can compute bcrypt hashes in parallel, albeit slowly. scrypt requires significant memory (typically 16-64 MB per hash computation), which limits GPU parallelism because GPUs have limited per-thread memory.

scrypt takes three parameters: N (CPU/memory cost), r (block size), and p (parallelism). Typical values are N=16384 (2^14), r=8, p=1, requiring about 16 MB of memory per hash. An attacker with a GPU that has 24 GB of memory can compute only about 1,500 hashes simultaneously (24,000 MB / 16 MB), compared to the GPU's thousands of available cores.

Argon2: The Current Best Practice

Argon2 won the Password Hashing Competition in 2015, evaluated by a panel of cryptographers. It comes in three variants: Argon2d (data-dependent memory access, resistant to GPU attacks), Argon2i (data-independent, resistant to side-channel attacks), and Argon2id (hybrid of both, the recommended variant).

Argon2id takes three tunable parameters: time cost (number of iterations), memory cost (in KB), and parallelism degree. The recommended minimum configuration is: memory 64 MB, time 3 iterations, parallelism 1. This produces a hash in about 250-500ms on modern server hardware.

Rainbow Tables: The Precomputation Attack

Instead of cracking passwords one at a time, an attacker can precompute a massive table of hash-to-password mappings. Given a stolen hash, they simply look it up in the table. No per-hash computation needed.

A rainbow table for all 8-character alphanumeric (62 chars) MD5 passwords requires storing 218 trillion (62^8) entries. Using the time-memory tradeoff that gives rainbow tables their name, this can be compressed to roughly 460 GB. The table takes weeks to generate but can then crack any matching password with a single disk lookup in seconds.

For all 8-character full-ASCII MD5 passwords, the table would need 6.6 quadrillion entries. Even with compression, this exceeds practical storage. But for shorter or less complex passwords, rainbow tables are devastatingly effective.

Why Salting Kills Rainbow Tables

A salt is a random value concatenated with the password before hashing. If two users have the password "hunter2," their hashes are different because each has a unique salt.

 User A: salt = "a8f2e1" -> hash("a8f2e1" + "hunter2") = 7c9e2f... User B: salt = "3b71d9" -> hash("3b71d9" + "hunter2") = e4a8b1...

A rainbow table built for unsalted hashes cannot crack salted hashes because the table does not include the salt values. The attacker would need a separate rainbow table for each possible salt value. With a 128-bit salt (standard for bcrypt), there are 3.4 * 10^38 possible salts. Building a rainbow table for each is computationally impossible.

This is why bcrypt, scrypt, and Argon2 all include automatic salting. It is not an optional feature. It is built into the algorithm. MD5 and SHA-256 do not include salting, so developers must add it manually (and many forget or do it incorrectly).

The 16-Lowercase-Beats-8-Complex Proof

I keep coming back to this because it is the single most important takeaway. Let me lay out the math one final time with complete rigor.

Password X: 8 characters, full ASCII (95 chars). Entropy = 52.56 bits. Keyspace = 95^8 = 6,634,204,312,890,625.

Password Y: 16 characters, lowercase (26 chars). Entropy = 75.21 bits. Keyspace = 26^16 = 43,608,742,899,428,874,000,000.

Ratio: Y/X = 6,573,370 (Password Y has 6.5 million times more combinations).

At 164 billion MD5 guesses per second, exhausting the entire keyspace takes 11.24 hours for Password X and 74,030 years for Password Y.

At 184 bcrypt-12 guesses per second, Password X takes 1.14 million years. Password Y takes 7.5 * 10^12 years (7.5 trillion years, or about 545 times the age of the universe).

Password Y (16 lowercase characters) is safer than Password X (8 full ASCII characters) by every measure. It is also easier to type, easier to remember (if it is a passphrase), and does not require holding shift or finding symbol keys.

The lesson for password policy: minimum length of 14-16 characters is more effective than requiring complexity on short passwords. NIST agrees. Their 2017 guidelines (SP 800-63B) explicitly recommend favoring length over complexity requirements.

Real-World Breach Data

Theory is one thing. What actually happens in breaches tells us how attackers operate and where passwords fail.

The RockYou breach (2009) exposed 32 million plaintext passwords. The top 10 passwords were: 123456, 12345, 123456789, password, iloveyou, princess, 1234567, rockyou, 12345678, abc123. The median password length was 7 characters. Over 290,000 users had the password "123456."

The LinkedIn breach (2012, disclosed 2016) exposed 164 million SHA-1 hashes without salts. Within days, security researchers cracked 117 million of them (71%). The most common password was "123456" followed by "linkedin" and "password." SHA-1 without salting made cracking trivial.

The Adobe breach (2013) exposed 153 million passwords encrypted with 3DES in ECB mode (not hashed, encrypted, and with a mode that revealed patterns). The password hints stored alongside the encrypted passwords made cracking even easier. Over 1.9 million users had "123456."

These breaches reveal two things. First, a huge percentage of users choose extremely weak passwords. Second, the storage method matters enormously. LinkedIn's unsalted SHA-1 meant that once one user's "password" was cracked, every user with that same password was instantly compromised (same input, same hash). Proper salting prevents this cascade.

Credential Stuffing: Why One Breach Becomes Many

When LinkedIn's passwords were cracked, attackers did not just access LinkedIn accounts. They tried those username/password pairs on Gmail, Facebook, Twitter, bank accounts, and every other service they could think of. This is credential stuffing.

Studies estimate that 65% of people reuse passwords across multiple accounts. If your LinkedIn password was "Surfing2014!" and you used the same password for your Gmail, the attacker logs into your email without cracking anything. From your email, they can reset passwords on your financial accounts. One breach cascades into total account compromise.

The mathematical defense against credential stuffing is not a stronger password. It is a unique password for every account. A password manager makes this practical. Each account gets a randomly generated 20+ character password that you never need to memorize. The password manager remembers all of them.

Quantum Computing: Should You Worry Yet?

Grover's algorithm, if implemented on a sufficiently powerful quantum computer, could theoretically halve the bit security of symmetric cryptographic operations (including password hashing). A 128-bit password would have 64-bit quantum security. A 64-bit password would have 32-bit quantum security, which is trivially crackable.

However, current quantum computers are nowhere near this capability. The largest demonstrated quantum computations as of early 2026 involve hundreds of logical qubits. Grover's algorithm against a 128-bit keyspace would require thousands of error-corrected logical qubits and millions of physical qubits. Most experts estimate practical cryptographic quantum computers are 10-20 years away, if they are achievable at all.

For now, a 128-bit entropy password (a 20-character random full-ASCII password or a 10-word passphrase) provides quantum-resistant security. This is already more than most people use.

The more immediate threat is that quantum computers could break public-key cryptography (RSA, ECC) via Shor's algorithm, which has polynomial rather than square-root speedup. This affects TLS, SSH, and other transport security, not password hashing directly. Post-quantum cryptographic standards (ML-KEM, ML-DSA) are already being deployed to address this.

Building Your Password Strategy

Based on everything above, here is what the math actually recommends.

Use a password manager. Generate a unique random password of 20+ characters for every account. You do not need to remember these passwords, so there is no reason to make them short or memorable. Let the math work in your favor with maximum entropy.

For your master password (the one you must remember), use a 6-word Diceware passphrase (77.5 bits of entropy). Generate it with actual dice or a cryptographic random source. Memorize it through repetition over the first week. This is the only password you need to remember.

Enable two-factor authentication on every account that supports it. Even if your password is compromised (through phishing, for example, which bypasses all password strength), 2FA prevents account access without the second factor.

For services you use daily and want quick access (phone PIN, laptop password), use a passphrase that balances security with typing convenience. A 4-word passphrase (51.7 bits) is acceptable for a device that has a lockout mechanism (10 attempts then wipe), because the attacker cannot do billions of guesses per second against a rate-limited interface.

Frequently Asked Questions

What is password entropy and how is it calculated?

Entropy = L * log2(C), where L is password length and C is the character set size. A 12-character password using 95 printable ASCII characters has 12 * 6.57 = 78.8 bits of entropy. Each additional bit doubles the number of guesses an attacker needs. Higher entropy means a harder-to-crack password.

Why is a long simple password stronger than a short complex one?

Length has an exponential effect. Each added character multiplies the keyspace by the character set size. A 16-character lowercase password has 75.2 bits of entropy (4.3 * 10^22 combinations). An 8-character full-ASCII password has only 52.6 bits (6.6 * 10^15 combinations). The longer password is 6.5 million times harder to crack.

How fast can modern hardware crack passwords?

A single RTX 4090 computes 164 billion MD5 hashes per second but only 184 bcrypt (cost 12) hashes per second. A cloud cluster can push MD5 throughput above 1 trillion per second. The hash algorithm determines attack speed far more than the hardware.

What is bcrypt and why is it better?

bcrypt is deliberately slow, with an adjustable cost factor that doubles computation per increment. At cost 12, one hash takes 250ms. It includes automatic salting. A single GPU manages about 184 bcrypt-12 guesses per second versus 164 billion for MD5. That factor of 891 million makes brute force against strong passwords infeasible.

What are rainbow tables?

Precomputed lookup tables mapping hash outputs back to inputs. Instead of computing during the attack, the attacker looks up the hash. Salting defeats rainbow tables because each password has a unique salt, requiring a separate table per salt. bcrypt, scrypt, and Argon2 include automatic salting.

Is "P@ssw0rd!" a strong password?

No. Despite containing uppercase, lowercase, numbers, and symbols, it is a predictable transformation of "password." Dictionary attacks include these substitution patterns. Its effective entropy is roughly 20-25 bits, not the 59 bits its character set would suggest. A random 4-word passphrase is far stronger.

What is the difference between Argon2, bcrypt, and scrypt?

All three are slow-by-design password hashing functions. bcrypt (1999) is CPU-hard. scrypt (2009) adds memory-hardness, limiting GPU attacks. Argon2id (2015) offers tunable CPU time, memory, and parallelism, and is the current best practice per the Password Hashing Competition.

How long would it take to crack my password?

It depends on length, character set, and hash algorithm. A 12-character full-ASCII password against MD5 takes about 1.8 million years. Against bcrypt-12, about 1.6 trillion years. But the same password in a plaintext leak is compromised instantly. Use a password generator to create strong random passwords.
