Color is not just a design concern. Every developer who writes CSS makes color decisions that affect usability, accessibility, brand perception, and conversion rates. Choosing a button background, setting up a dark mode theme, building a data visualization -- these all require color decisions. Understanding color theory gives you the foundation to make informed choices instead of guessing.

Color Models for the Web

A color model is a mathematical system for describing colors as numbers. The web supports several color models, each with different strengths. Understanding how they work helps you manipulate colors programmatically and communicate color choices clearly.

RGB (Red, Green, Blue)

RGB is the native color model of screens. Every pixel on your monitor is composed of red, green, and blue subpixels at varying intensities. RGB values range from 0 (off) to 255 (full intensity) for each channel, giving 16,777,216 possible colors (256 x 256 x 256).

/* RGB notation in CSS */
color: rgb(0, 255, 136);         /* Zovo accent green */
color: rgb(224, 224, 232);       /* light text */
color: rgba(0, 255, 136, 0.15);  /* accent with 15% opacity */

The hex notation is a compact representation of RGB. #00ff88 means red=0 (00), green=255 (ff), blue=136 (88). Each pair of hex digits represents one channel. The shorthand #0f8 expands to #00ff88 by doubling each digit.

RGB is straightforward for the browser to process because it maps directly to hardware, but it is unintuitive for humans. If I ask you to make a color "slightly warmer" or "a bit more muted," adjusting the red, green, and blue channels independently to achieve that is not obvious. This is why HSL was created.

Hex Notation

Hex is the most common color format in web development. It is compact, widely supported, and easy to copy between tools. The format is #RRGGBB, where each pair represents one RGB channel in hexadecimal (base 16).

/* Common hex formats */
#000000  /* black */
#ffffff  /* white */
#00ff88  /* Zovo green */
#00ccff  /* Zovo blue */
#ff4466  /* error red */

/* 8-digit hex includes alpha channel */
#00ff8826  /* Zovo green at ~15% opacity (26 in hex = 38 in decimal = 38/255 = ~15%) */

/* 3-digit shorthand (each digit doubled) */
#fff     /* same as #ffffff */
#000     /* same as #000000 */

HSL: The Developer's Color Model

HSL (Hue, Saturation, Lightness) describes colors the way humans think about them. Hue is the color itself (red, blue, green, yellow), expressed as a degree on the color wheel from 0 to 360. Saturation is the intensity of the color, from 0% (gray) to 100% (vivid). Lightness is how light or dark the color is, from 0% (black) to 100% (white).

/* HSL notation in CSS */
color: hsl(152, 100%, 50%);    /* Zovo accent green */
/*         ^     ^      ^
           |     |      +-- lightness: 50% (pure color)
           |     +--------- saturation: 100% (vivid)
           +--------------- hue: 152 degrees (green) */

HSL is the most useful color model for web development because it maps to intuitive color operations. To make a color lighter, increase the lightness. To make it more muted, decrease the saturation. To shift the color toward a warmer or cooler temperature, adjust the hue. To create a set of related colors, keep the hue constant and vary saturation and lightness.

Creating Color Scales with HSL

One of the most practical applications of HSL is generating color scales for design systems. A color scale is a series of shades of the same color, from very light to very dark, used for backgrounds, borders, text, and interactive states.

:root {
    /* Green scale - same hue (152), same saturation, varying lightness */
    --green-50:  hsl(152, 100%, 97%);  /* lightest, for backgrounds */
    --green-100: hsl(152, 100%, 92%);
    --green-200: hsl(152, 100%, 80%);
    --green-300: hsl(152, 100%, 65%);
    --green-400: hsl(152, 100%, 55%);
    --green-500: hsl(152, 100%, 50%);  /* primary, the "brand" shade */
    --green-600: hsl(152, 100%, 42%);
    --green-700: hsl(152, 100%, 34%);
    --green-800: hsl(152, 100%, 26%);
    --green-900: hsl(152, 100%, 18%);  /* darkest, for text on light */
}

In practice, good color scales adjust saturation as well as lightness. Very light shades often need slightly lower saturation to avoid looking washed out, and very dark shades need slightly higher saturation to maintain color presence. The best tools for generating these scales account for perceptual uniformity, which means the visual difference between each step appears equal to the human eye.

Modern CSS Color Functions

CSS has evolved beyond basic RGB and HSL with new color functions that provide more control and perceptual accuracy. These modern functions are supported in all major browsers as of 2025.

oklch() and oklab()

The oklch() function uses the OKLCH color space, which is perceptually uniform. This means that changing the lightness value by the same amount always produces the same visual change, regardless of the hue. In HSL, changing the lightness of a yellow and a blue by the same amount produces different perceived brightness changes because HSL does not account for how the human eye perceives different wavelengths.

/* OKLCH: lightness, chroma (saturation), hue */
color: oklch(0.87 0.3 152);     /* vivid green */
color: oklch(0.87 0.15 152);    /* muted green (lower chroma) */
color: oklch(0.6 0.3 152);      /* darker green (lower lightness) */

/* The perceptual uniformity means:
   oklch(0.5 0.2 0)   - red at 50% perceived lightness
   oklch(0.5 0.2 240) - blue at 50% perceived lightness
   These actually LOOK equally bright, unlike hsl(0, 80%, 50%) vs hsl(240, 80%, 50%) */

I recommend using oklch() for any project started in 2025 or later. It makes color manipulation predictable and eliminates the perceptual inconsistencies of HSL. When you decrease the chroma (saturation) of a color in OKLCH, it fades evenly toward gray without unexpected hue shifts. When you adjust lightness, the perceived brightness change is consistent across all hues.

color-mix()

The color-mix() function blends two colors in a specified color space. This is incredibly useful for creating hover states, focus indicators, and dynamic color variations without defining every shade manually.

:root {
    --accent: #00ff88;
}

.button {
    background: var(--accent);
}

.button:hover {
    /* Mix accent with white to lighten */
    background: color-mix(in oklch, var(--accent) 80%, white);
}

.button:active {
    /* Mix accent with black to darken */
    background: color-mix(in oklch, var(--accent) 80%, black);
}

.surface {
    /* Mix accent with the background for a tinted surface */
    background: color-mix(in oklch, var(--accent) 10%, #12121a);
}

The in oklch specifier tells the browser to perform the mixing in the OKLCH color space, which produces more natural-looking results than mixing in sRGB. Mixing in sRGB can produce muddy intermediate colors, especially when blending colors on opposite sides of the color wheel.

Relative Color Syntax

The relative color syntax (supported since Chrome 119 and Safari 16.4) lets you derive new colors by modifying individual channels of an existing color. This is significant for creating color systems from a single base color.

:root {
    --brand: oklch(0.7 0.25 152);

    /* Derive all variants from the brand color */
    --brand-light: oklch(from var(--brand) calc(l + 0.2) c h);
    --brand-dark: oklch(from var(--brand) calc(l - 0.2) c h);
    --brand-muted: oklch(from var(--brand) l calc(c * 0.5) h);
    --brand-bg: oklch(from var(--brand) 0.15 calc(c * 0.3) h);
}

Contrast: The Most Important Color Concept

Contrast ratio is the single most important color metric in web development. It determines whether text is readable, whether buttons are distinguishable from backgrounds, and whether your interface is usable by people with visual impairments. Poor contrast is the most common accessibility violation on the web, found on 83% of home pages according to the WebAIM Million study in 2025.

How Contrast Ratio Works

Contrast ratio is calculated by comparing the relative luminance of two colors. The formula produces a ratio between 1:1 (no contrast, identical colors) and 21:1 (maximum contrast, pure black on pure white). The formula defined in WCAG 2.x converts both colors to relative luminance values and divides the lighter value by the darker value.

// Simplified contrast ratio calculation
function getContrastRatio(color1, color2) {
    const lum1 = getRelativeLuminance(color1);
    const lum2 = getRelativeLuminance(color2);
    const lighter = Math.max(lum1, lum2);
    const darker = Math.min(lum1, lum2);
    return (lighter + 0.05) / (darker + 0.05);
}

function getRelativeLuminance(rgb) {
    const [r, g, b] = rgb.map(c => {
        c = c / 255;
        return c <= 0.03928 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4);
    });
    return 0.2126 * r + 0.7152 * g + 0.0722 * b;
}

// Example
getContrastRatio([224, 224, 232], [10, 10, 15]); // ~15.8:1 (excellent)

WCAG Accessibility Requirements

The Web Content Accessibility Guidelines (WCAG) define minimum contrast ratios for text and interactive elements. Meeting these requirements is not optional. It is a legal requirement in many jurisdictions (ADA in the US, EN 301 549 in the EU) and a fundamental aspect of making your interface usable by all users.

WCAG 2.2 Contrast Requirements

Element Level AA (minimum) Level AAA (enhanced)
Normal text (under 18px or under 14px bold)4.5:17:1
Large text (18px+ or 14px+ bold)3:14.5:1
UI components and graphical objects3:1Not defined
Focus indicators3:1Not defined

Level AA is the standard target for most websites. Level AAA is the enhanced target used by organizations with strong accessibility commitments, government agencies, and applications for older users or users with known visual impairments.

Practical Contrast Guidelines

Body text should have a contrast ratio of at least 4.5:1. On a dark background like #0a0a0f, this means text needs to be at least as light as #767676 (and that is the absolute minimum; I recommend 7:1 or higher for body text). The Zovo text color #e0e0e8 on background #0a0a0f achieves approximately 15.8:1, which exceeds even AAA requirements.

For links, buttons, and interactive elements, the color must have 3:1 contrast against the adjacent background. The Zovo accent green #00ff88 on background #0a0a0f achieves approximately 13.9:1, which is excellent. However, if you used that same green for small text on a lighter surface, you would need to verify the ratio meets the 4.5:1 threshold for normal text.

Common mistake: Placeholder text in form inputs is one of the most frequently failing contrast elements. Designers often use very light gray placeholder text for aesthetic reasons, but if the placeholder serves as the label (which is itself an accessibility anti-pattern), the contrast must meet 4.5:1. Even if a separate label exists, placeholders should have at least 3:1 contrast as a UI component.

APCA: The Next Generation of Contrast

The WCAG 3.0 working draft introduces APCA (Advanced Perceptual Contrast Algorithm) as a replacement for the current contrast ratio formula. APCA is designed to be more perceptually accurate, accounting for factors like font weight, font size, and the polarity of the color pair (dark text on light vs light text on dark). Under the current WCAG 2.x formula, some color pairs that are technically compliant still look hard to read, while some non-compliant pairs are perfectly readable. APCA aims to fix these edge cases.

While WCAG 3.0 is still in development, APCA is available for testing and provides a useful second opinion alongside the standard contrast ratio. The key difference is that APCA returns a "lightness contrast" value (Lc) that accounts for the direction of the contrast. Dark text on light background and light text on dark background at the same luminance levels have different readability characteristics, and APCA captures this asymmetry.

Designing for Color Blindness

Approximately 8% of men and 0.5% of women have some form of color vision deficiency. This means that in a room of 25 people, statistically two of them see colors differently than you do. If your interface relies on color alone to convey information, those you will miss the information entirely.

Types of Color Blindness

Type Prevalence Colors Affected
Deuteranopia (green-blind)~5% of malesRed and green appear similar
Protanopia (red-blind)~2.5% of malesRed and green appear similar, reds appear darker
Tritanopia (blue-blind)~0.01% of populationBlue and yellow appear similar
Achromatopsia (total color blind)~0.003% of populationAll colors appear as shades of gray

Red-green color blindness (deuteranopia and protanopia combined) affects approximately 7.5% of males. This has direct implications for the extremely common practice of using red for errors and green for success. To a user with red-green color blindness, a red error message and a green success message may look identical in color. Both appear as a muddy olive or brown shade.

Practical Guidelines

  • Never use color as the only indicator of meaning. Pair colors with icons, text labels, patterns, or positional cues. A form field with an error should not rely solely on a red border. Add an error icon and descriptive text.
  • Use lightness contrast in addition to hue contrast. Two colors that look identical to a colorblind user in terms of hue may still be distinguishable if they have different lightness values. A dark red and a light green are distinguishable by brightness even if the hues blend together.
  • Test your designs with color blindness simulation tools. Our Color Blindness Simulator shows you exactly how your color choices look to users with different types of color vision deficiency.
  • In charts and data visualizations, use patterns (dashes, dots, crosshatch) in addition to colors. Distinguish data series by shape (circles, squares, triangles) as well as color. Provide direct labels on data rather than relying on a color-coded legend.
  • Avoid problematic color pairs: red/green, red/brown, green/brown, blue/purple, green/blue. These are the combinations most likely to cause confusion for colorblind users.

Quick test: Convert your interface to grayscale (you can do this in Chrome DevTools under Rendering, then "emulate vision deficiencies" and select "achromatopsia"). If you can still understand every piece of information and distinguish every interactive element, your design is colorblind-safe. If anything becomes ambiguous, add non-color visual cues. Color Psychology in Interface Design

Color psychology is the study of how colors influence human perception, emotion, and behavior. While some color psychology claims are overstated or culturally dependent, several effects are well-documented in research and directly relevant to interface design.

Trust and Credibility

Blue is consistently associated with trust, reliability, and professionalism across Western cultures. This is not just folklore. Studies published in the journal Color Research and Application found that blue interfaces were rated as more trustworthy than equivalent interfaces in other colors. This explains why financial institutions (Chase, PayPal, Venmo, Capital One), social media platforms (Facebook, LinkedIn, Twitter/X), and enterprise software (Salesforce, Atlassian, Slack) overwhelmingly choose blue as their primary brand color.

However, trust is not solely about color. A trustworthy-looking blue interface with poor usability, slow performance, or unclear information architecture will still fail to earn user trust. Color supports the perception of trustworthiness, but it cannot create it from nothing.

Urgency and Action

Red is associated with urgency, importance, and immediate action. This makes it effective for error messages, warning states, and clearance sale promotions. Research on e-commerce conversion found that red call-to-action buttons outperformed green buttons by 21% in one widely cited HubSpot study, though the effect depends heavily on the surrounding context. A red button on a page that is already predominantly red has no contrast advantage.

Orange shares the urgency association with red but is perceived as less threatening and more friendly. This makes it effective for primary action buttons and attention-grabbing elements where red would be too aggressive. Amazon's "Add to Cart" button uses orange precisely for this balance of urgency and approachability.

Green for Confirmation

Green is universally associated with success, approval, go, and positive outcomes. Use green for success messages, completed states, positive metrics, and confirmation actions. The Zovo accent green #00ff88 uses this association effectively. It communicates energy and positivity while maintaining a modern, technical feel due to its brightness and saturation.

Neutral Colors and Content Focus

Neutral colors (grays, off-whites, dark backgrounds) direct attention to content rather than the interface itself. The most successful content-focused applications use predominantly neutral palettes with a single accent color for interactive elements. This minimizes visual noise and maximizes content readability. The Zovo dark theme (#0a0a0f background, #e0e0e8 text) exemplifies this approach: the near-black background disappears from conscious perception, letting the content and accent colors take full focus.

Building a Color Palette from Scratch

A well-structured color palette for a web application typically needs five categories of colors. Here is the systematic approach I use for every project.

Step 1: Choose One Primary Color

Start with a single color that represents the brand or product identity. This color will be used for primary buttons, active states, links, and key visual elements. It should be distinctive, work on both light and dark backgrounds (or you will need variants), and align with the emotional tone of the product.

For the Zovo tools site, the primary color is #00ff88, a vivid mint green that conveys technical precision and modernity. I chose it because it provides excellent contrast on dark backgrounds, stands out without being aggressive, and differentiates the brand from the sea of blue tech websites.

Step 2: Generate the Primary Scale

From the primary color, generate a 10-step scale from very light (for backgrounds and subtle highlights) to very dark (for text and borders on light surfaces). Using HSL or OKLCH, keep the hue consistent and vary lightness and saturation.

:root {
    /* Primary color scale */
    --primary-50:  oklch(0.97 0.05 152);   /* tinted white */
    --primary-100: oklch(0.92 0.10 152);   /* light background */
    --primary-200: oklch(0.82 0.18 152);   /* lighter accent */
    --primary-300: oklch(0.72 0.22 152);   /* medium light */
    --primary-400: oklch(0.65 0.26 152);   /* medium */
    --primary-500: oklch(0.87 0.30 152);   /* primary (brand color) */
    --primary-600: oklch(0.55 0.22 152);   /* medium dark */
    --primary-700: oklch(0.45 0.18 152);   /* dark */
    --primary-800: oklch(0.35 0.14 152);   /* darker */
    --primary-900: oklch(0.25 0.10 152);   /* darkest */
}

Step 3: Define Semantic Colors

Semantic colors communicate meaning regardless of the brand. Every web application needs at minimum success (green), warning (amber/yellow), error/danger (red), and info (blue). These should be distinct from the primary color to avoid confusion.

:root {
    --success: oklch(0.72 0.20 145);   /* green */
    --warning: oklch(0.80 0.18 85);    /* amber */
    --error:   oklch(0.63 0.24 25);    /* red */
    --info:    oklch(0.70 0.15 240);   /* blue */
}

Step 4: Build the Neutral Scale

The neutral scale is the backbone of your interface. It provides colors for backgrounds, text, borders, disabled states, and secondary UI elements. A good neutral scale has 10 to 12 steps and should have a very slight tint of your primary hue to create visual cohesion.

:root {
    /* Neutrals with a subtle green-blue tint (hue ~220) */
    --gray-50:  oklch(0.98 0.003 220);   /* lightest background */
    --gray-100: oklch(0.95 0.005 220);   /* card background (light mode) */
    --gray-200: oklch(0.90 0.008 220);   /* borders (light mode) */
    --gray-300: oklch(0.82 0.010 220);   /* disabled text */
    --gray-400: oklch(0.70 0.012 220);   /* placeholder text */
    --gray-500: oklch(0.58 0.012 220);   /* secondary text */
    --gray-600: oklch(0.47 0.012 220);   /* body text (light mode) */
    --gray-700: oklch(0.37 0.012 220);   /* headings (light mode) */
    --gray-800: oklch(0.25 0.015 220);   /* card background (dark mode) */
    --gray-900: oklch(0.17 0.015 220);   /* background (dark mode) */
    --gray-950: oklch(0.10 0.015 220);   /* deepest background */
}

The slight chroma (0.003 to 0.015) in the neutrals prevents them from looking flat or lifeless. Pure gray (#808080) has zero chroma, which can make an interface feel sterile. Adding a hint of color to your neutrals, matching the hue of your primary color, creates subtle warmth and visual coherence.

Step 5: Define Functional Tokens

Functional tokens map semantic purposes to specific colors from your scales. This abstraction layer lets you change the entire color system by modifying the scale values without touching component styles.

:root {
    /* Functional tokens for dark mode */
    --color-bg:         var(--gray-950);
    --color-surface:    var(--gray-900);
    --color-border:     var(--gray-800);
    --color-text:       var(--gray-100);
    --color-text-muted: var(--gray-500);
    --color-link:       var(--primary-500);
    --color-link-hover: var(--primary-400);
    --color-focus-ring: var(--primary-500);
}

/* Switch to light mode by remapping tokens */
@media (prefers-color-scheme: light) {
    :root {
        --color-bg:         var(--gray-50);
        --color-surface:    white;
        --color-border:     var(--gray-200);
        --color-text:       var(--gray-700);
        --color-text-muted: var(--gray-500);
        --color-link:       var(--primary-700);
        --color-link-hover: var(--primary-600);
        --color-focus-ring: var(--primary-500);
    }
}

Dark Mode Color Strategy

Dark mode is no longer optional for most web applications. User preferences have shifted, with surveys indicating that over 80% of users enable dark mode when available. Operating systems, browsers, and CSS provide native support for detecting and responding to the user's preferred color scheme.

Dark Mode Is Not Just Inverted Colors

The most common mistake in dark mode implementation is simply inverting the light mode palette. True white text on true black backgrounds creates excessive contrast that causes eye strain during extended reading. Vibrant colors that look great on a white background can appear overly glaring on a dark background. Shadows that add depth in light mode are invisible in dark mode.

Effective dark mode requires thoughtful adjustment. Here are the principles I follow.

Reduce maximum contrast. Instead of pure white #ffffff on pure black #000000 (21:1 ratio), use off-white text #e0e0e8 on near-black backgrounds #0a0a0f (approximately 15.8:1). This exceeds WCAG AAA requirements while being significantly more comfortable for extended reading.

Desaturate accent colors slightly. Colors that look balanced at 100% saturation on a white background can appear neon and glaring on a dark background. Reducing saturation by 10 to 20 percent often produces a more comfortable result. Alternatively, increase the lightness slightly to reduce the perceived contrast between the accent color and the dark background.

Use elevation instead of shadows. In light mode, cards appear to float above the background through box shadows. In dark mode, improve surfaces by making them slightly lighter than the background. A card at #12121a on a background of #0a0a0f creates a subtle sense of depth through lightness difference rather than shadow.

/* Dark mode elevation system */
:root {
    --elevation-0: #0a0a0f;   /* base background */
    --elevation-1: #12121a;   /* cards, surfaces */
    --elevation-2: #1a1a26;   /* dropdown menus, popovers */
    --elevation-3: #222232;   /* modal overlays */
    --elevation-4: #2a2a3a;   /* tooltips, highest elevation */
}

/* Each level is slightly lighter, creating visual hierarchy
   without relying on shadows */

Color in Design Systems

A design system's color implementation should provide enough flexibility for diverse UI needs while maintaining consistency across products and teams. Here is the architecture I recommend.

Three-Layer Token System

Layer 1 contains primitive tokens, which are the raw color values with no semantic meaning: --blue-500, --gray-200, --red-600. These are the palette definition and rarely change.

Layer 2 contains semantic tokens, which map purposes to primitives: --color-text-primary, --color-bg-surface, --color-border-error. These change when you switch themes (light mode to dark mode) or brands.

Layer 3 contains component tokens, which are specific to individual components: --button-bg, --card-border, --input-focus-ring. These reference semantic tokens and provide an override point for component-level customization.

/* Layer 1: Primitives */
:root {
    --blue-500: oklch(0.62 0.22 255);
    --gray-100: oklch(0.95 0.005 220);
}

/* Layer 2: Semantic tokens */
:root {
    --color-interactive: var(--blue-500);
    --color-bg-subtle: var(--gray-100);
}

/* Layer 3: Component tokens */
.button-primary {
    --button-bg: var(--color-interactive);
    --button-text: white;
    background: var(--button-bg);
    color: var(--button-text);
}

/* A specific context can override at any layer */
.promotional-banner .button-primary {
    --button-bg: var(--orange-500);
}

This layered approach means that changing from a blue brand to a green brand requires updating only the semantic token mappings. All components automatically inherit the new colors because they reference semantic tokens, not primitive values.

Common Color Mistakes and How to Fix Them

Mistake 1: Too Many Colors

A professional interface typically needs 1 to 2 primary accent colors, 4 semantic colors (success, warning, error, info), and a neutral scale. That is it. Adding more colors introduces visual noise, increases maintenance burden, and makes the interface harder to learn. If you find yourself using more than 5 distinct hues in a single view, consolidate.

Mistake 2: Color Without Context

A button color that looks great in a mockup against a white background may perform poorly against a dark surface, inside a colored card, or adjacent to another colored element. Always test colors in their actual usage context, not in isolation. Component-level testing with the contrast checker is essential.

Mistake 3: Ignoring State Colors

Interactive elements need distinct colors for default, hover, active, focus, and disabled states. A common shortcut is to only define the default color and wing the rest. This leads to inconsistent interaction feedback. Define your state colors systematically: hover is typically 10% lighter or darker than default, active is 20% lighter or darker, focus uses a ring in the primary color, and disabled reduces opacity to 40 to 60%.

.button {
    --base: oklch(0.62 0.22 152);
    background: var(--base);
    transition: background 0.15s;
}

.button:hover {
    background: oklch(from var(--base) calc(l + 0.07) c h);
}

.button:active {
    background: oklch(from var(--base) calc(l - 0.05) c h);
}

.button:focus-visible {
    outline: 2px solid var(--base);
    outline-offset: 2px;
}

.button:disabled {
    opacity: 0.5;
    cursor: not-allowed;
}

Mistake 4: Not Testing on Real Screens

Colors look different on different screens. A color-calibrated design monitor displays colors very differently from a budget laptop screen or a phone in direct sunlight. Test your color choices on multiple devices and in multiple lighting conditions. Pay particular attention to contrast on low-quality displays where colors tend to appear more washed out.

Mistake 5: Hardcoding Colors

Scattering hex codes throughout your CSS makes it nearly impossible to maintain a consistent palette or make global changes. Every color should be defined as a CSS custom property (variable) and referenced by name. This makes theming, dark mode, and brand updates manageable.

/* Never do this */
.header { background: #12121a; }
.sidebar { background: #12121a; }
