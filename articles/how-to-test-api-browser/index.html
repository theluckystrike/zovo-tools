Common mistakes covered

I have spent the better part of six years building Chrome extensions and web tools, and every one of those projects started the same way. Before I wrote a single line of integration code, I tested the target API by hand. Not because I lacked confidence in the documentation, but because documentation lies. Endpoints change. Authentication flows have quirks that no README ever captures. Rate limits kick in at thresholds different from what the docs promise.

Testing an API before writing integration code is the single most reliable way to avoid debugging phantom issues later. You discover the actual response shape, confirm authentication requirements, measure real latency, and identify edge cases that only surface when you send a request yourself. This guide covers every practical method for testing REST APIs, starting with the tools already built into your browser and working outward to dedicated clients.

Representational State Transfer (REST)
REST is an architectural style for distributed hypermedia systems. It was first defined by Roy Fielding in his 2000 doctoral dissertation at UC Irvine. RESTful APIs use HTTP methods (GET, POST, PUT, PATCH, DELETE) to perform operations on resources identified by URIs. The style emphasizes statelessness, uniform interfaces, and the separation of client and server concerns. While REST is not a formal protocol, its conventions have become the dominant approach for web API design, with JSON as the standard data interchange format since approximately 2012.

Why Testing APIs Matters Before Writing Integration Code

The gap between API documentation and actual API behavior is wider than most developers expect. I have worked with APIs where the documented response schema was three versions behind the live endpoint. I have seen APIs that returned 200 status codes for error conditions, with the actual error buried inside a nested JSON property. I have encountered rate-limiting behavior that differed between staging and production environments with no documentation about the difference.

Manual testing catches these issues before they become debugging sessions at 2 AM. When you send a request by hand and inspect the raw response, you learn things that no SDK wrapper or code example can teach you. You see the actual headers the server returns, including cache-control directives, rate-limit counters, and pagination metadata. You discover whether the API returns null, an empty string, or omits keys entirely when a field has no value. You find out whether dates come back as ISO 8601 strings, Unix timestamps, or some custom format the documentation forgot to mention.

There is also a practical speed argument. Spinning up a quick test in your browser console takes 30 seconds. Writing a test script, importing an HTTP library, handling the response, and running the file takes several minutes. When you are exploring an API for the first time, the feedback loop of manual testing is substantially faster.

The tools I cover in this guide range from zero-install (your browser console) to full-featured desktop applications. Each has a legitimate place in the workflow. The right choice depends on what you are testing, how often you will repeat the test, and whether you need to share the results with a team.

Using fetch() in the DevTools Console

Every modern browser ships with a fully functional HTTP client built into the developer console. The Fetch API, available in every browser since 2015, lets you send GET, POST, PUT, PATCH, and DELETE requests without installing anything at all. I use this approach more than any other tool when I am exploring a new API for the first time.

Sending a GET request

Open DevTools with F12 or Ctrl+Shift+J (Windows/Linux) or Cmd+Option+J (macOS). Click the Console tab. Type or paste the following:

fetch('https://jsonplaceholder.typicode.com/posts/1')
  .then(response => response.json())
  .then(data => console.log(data))
  .catch(error => console.error('Request failed:', error));

Press Enter. The response appears directly in the console, formatted as an expandable JavaScript object. You can click into nested properties, copy values, and inspect the data structure without leaving the browser tab you already have open.

For a cleaner syntax, use async/await inside an immediately invoked async function:

(async () => {
  try {
    const response = await fetch('https://jsonplaceholder.typicode.com/posts/1');
    const data = await response.json();
    console.log('Status:', response.status);
    console.log('Headers:', Object.fromEntries(response.headers));
    console.log('Body:', data);
  } catch (err) {
    console.error('Failed:', err);
  }
})();

This version gives you the status code, response headers, and body in separate console entries, which makes it easier to inspect each piece independently.

Sending a POST request with JSON body

POST requests require additional configuration for the method, headers, and body:

(async () => {
  const response = await fetch('https://jsonplaceholder.typicode.com/posts', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      title: 'Testing from DevTools',
      body: 'This request was sent from the browser console.',
      userId: 1,
    }),
  });
  const data = await response.json();
  console.log('Status:', response.status);
  console.log('Response:', data);
})();

The Content-Type: application/json header is critical. Without it, many APIs will reject the request or misparse the body. I have seen developers spend an hour debugging a 400 Bad Request error that was caused entirely by a missing Content-Type header.

Sending requests with authentication

Bearer token authentication is the most common pattern for REST APIs:

(async () => {
  const response = await fetch('https://api.example.com/user/profile', {
    headers: {
      'Authorization': 'Bearer YOUR_ACCESS_TOKEN_HERE',
      'Content-Type': 'application/json',
    },
  });
  const data = await response.json();
  console.log(data);
})();

For APIs that use API key authentication via query parameters:

(async () => {
  const response = await fetch(
    'https://api.example.com/data?api_key=YOUR_KEY&format=json'
  );
  const data = await response.json();
  console.log(data);
})();

Limitations of the console approach

The DevTools console has real constraints. CORS (Cross-Origin Resource Sharing) policies will block requests to APIs that do not include your origin in their Access-Control-Allow-Origin header. If you are on https://google.com and try to fetch from https://api.github.com, the browser will block the request. You can partially work around this by navigating to the API's own domain first, or by opening a blank tab (about:blank) which has a null origin. But CORS restrictions remain the primary reason developers reach for dedicated API testing tools.

There is also no built-in way to save requests, organize them into collections, or share them with teammates. Each session is ephemeral. For one-off exploration, that is perfectly fine. For repeated testing, you need something more structured.

The curl Command Line Approach

curl is the universal HTTP client. It ships preinstalled on macOS and most Linux distributions. Windows 10 and later include it as well. If you have a terminal open, you have curl.

Basic GET request

curl https://jsonplaceholder.typicode.com/posts/1

This prints the raw response body to your terminal. Add the -i flag to include response headers:

curl -i https://jsonplaceholder.typicode.com/posts/1

The output now shows the HTTP status line, all response headers, and then the body. This is invaluable for debugging caching behavior, checking rate-limit headers, and verifying content types.

POST request with JSON

curl -X POST https://jsonplaceholder.typicode.com/posts \
  -H "Content-Type: application/json" \
  -d '{"title":"Test Post","body":"Sent via curl","userId":1}'

The -X flag specifies the HTTP method. -H adds a header. -d sends data in the request body. The backslashes at the end of each line are line continuations for readability; you can write the entire command on one line if you prefer.

Authentication with curl

# Bearer token
curl -H "Authorization: Bearer YOUR_TOKEN" \
  https://api.example.com/user/profile

# Basic auth (username:password)
curl -u username:password \
  https://api.example.com/protected/resource

# API key in header
curl -H "X-API-Key: YOUR_API_KEY" \
  https://api.example.com/data

Formatting curl output with jq

Raw JSON output from curl is hard to read. Pipe it through jq for formatted, syntax-highlighted output:

curl -s https://jsonplaceholder.typicode.com/posts/1 | jq .

# Extract specific fields
curl -s https://jsonplaceholder.typicode.com/posts | jq '.[0:3] | .[] | {id, title}'

# Filter by condition
curl -s https://jsonplaceholder.typicode.com/posts | jq '[.[] | select(.userId == 1)]'

If jq is not installed, python3 -m json.tool works as a fallback on any system with Python:

curl -s https://jsonplaceholder.typicode.com/posts/1 | python3 -m json.tool

curl excels at scripting and automation. You can save complex requests as shell scripts, chain them together with pipes, and integrate them into CI/CD pipelines. The tradeoff is that curl lacks a graphical interface, making it slower for exploratory work where you want to rapidly tweak parameters and inspect responses visually.

Hoppscotch as a Free Postman Alternative

Hoppscotch (formerly Postwoman) is a free, open-source API testing platform that runs entirely in the browser. Navigate to hoppscotch.io and you have a complete API testing environment without installing anything or creating an account.

What makes Hoppscotch stand out

The interface loads in under two seconds. There is no Electron wrapper, no multi-gigabyte install, and no sign-in gate blocking basic functionality. You type a URL, select a method, add headers if needed, and send. The response appears with syntax highlighting, response time measurement, and size calculation.

Hoppscotch supports REST, GraphQL, WebSocket, SSE (Server-Sent Events), Socket.IO, and MQTT. For most developers, the REST and GraphQL features are the primary draw, but having WebSocket testing in the same tool eliminates the need for separate WebSocket debugging utilities.

Key features for API testing

  • Environment variables for switching between development, staging, and production endpoints without editing each request
  • Pre-request scripts for generating dynamic values like timestamps or HMAC signatures
  • Collections for organizing related requests into logical groups
  • Request history that persists in local storage, so you can revisit previous tests without rebuilding them
  • Import from Postman, OpenAPI, curl, and HAR formats
  • Team collaboration with shared workspaces (requires free account)

GraphQL testing in Hoppscotch

The GraphQL tab provides schema introspection, query auto-completion, and variable management. Point it at any GraphQL endpoint and it fetches the schema automatically, then offers IntelliSense-style suggestions as you type your query. This is noticeably faster than building GraphQL queries in a generic REST client where you have to refer to the schema documentation separately.

Self-hosted option

For teams working with internal APIs that cannot be tested through a public website, Hoppscotch offers a self-hosted community edition. Deploy it on your own infrastructure and test private endpoints without routing requests through third-party servers. The self-hosted version is the same codebase as the public site, with Docker and Docker Compose deployment configurations provided.

The main limitation of Hoppscotch is the same CORS constraint that affects the DevTools console. Requests sent from the browser tab are subject to the browser's same-origin policy. Hoppscotch provides a browser extension proxy and a CLI tool to bypass this, but those require additional installation steps.

Thunder Client in VS Code

If you spend most of your working hours in Visual Studio Code, Thunder Client integrates API testing directly into your editor. Install it from the VS Code extension marketplace (the extension ID is rangav.vscode-thunder-client), and a lightning bolt icon appears in the activity bar.

Why developers prefer Thunder Client

Context switching is expensive. Opening a separate application to test an API, then switching back to your editor to write integration code, then switching back to the testing tool to verify a different endpoint, fragments your attention. Thunder Client keeps everything in one window. You write code in one pane and test the API in another. Copy a response value, paste it into your code, and continue working.

Features that matter for daily use

Thunder Client supports collections, environment variables, request chaining (where the output of one request feeds into another), and local storage of all data. The lightweight design is intentional. Where Postman has grown into a full API development platform with mock servers, monitoring, and team management features, Thunder Client focuses on the core task of sending HTTP requests and reading responses.

The free tier covers individual use with unlimited requests, collections, and environments stored locally. The paid tier adds Git sync and team collaboration features. For solo developers and small teams, the free version is sufficient.

Testing workflows in Thunder Client

A typical workflow involves creating a collection for each API you integrate with, organizing requests by resource type, and using environment variables for base URLs and authentication tokens. When you switch from development to staging, you change one environment selection instead of editing every request.

Thunder Client also supports scripting with JavaScript in pre-request and post-request hooks, which is useful for generating OAuth signatures, extracting tokens from login responses, and validating response schemas.

Postman for the Full Suite

Postman has been the default API testing tool for over a decade. It started as a Chrome extension in 2012, evolved into a standalone Electron application, and has since grown into a full API development platform. As of 2026, Postman reports over 30 million registered users.

When Postman is the right choice

Postman is the right tool when your API testing needs extend beyond sending individual requests. If you need to create mock servers that simulate API responses before the backend is built, Postman handles that. If you need to monitor APIs on a schedule and get alerts when response times degrade or schemas change, Postman handles that. If you need to generate API documentation from your request collections, Postman handles that.

For teams, Postman's workspace sharing lets developers collaborate on API testing without emailing curl commands or sharing JSON files. A QA engineer can run the same collection against a staging environment. A frontend developer can use mock servers to build against an API that does not exist yet. A technical writer can generate documentation directly from tested requests.

The complexity tradeoff

Postman's feature depth comes with weight. The desktop application is an Electron app that typically consumes 400-800 MB of memory. The interface has accumulated features across a dozen years of development, and new users often find it overwhelming. The free tier now requires sign-in, and certain features that were previously free have moved to paid plans.

For individual developers who need to send requests and read responses, Postman is more tool than necessary. I reach for Postman when I am building something that requires mock servers, automated test suites, or team collaboration. For quick API exploration, lighter alternatives are faster to start and easier to use.

API Testing PRO for In-Browser Testing

I built API Testing PRO as a Chrome extension because I wanted a middle ground that none of the existing tools occupied. DevTools fetch() is too ephemeral. Hoppscotch is a separate browser tab that cannot access the cookies and session state of the page I am currently working on. Postman is a separate application entirely. Thunder Client requires VS Code to be open. What I wanted was a lightweight testing interface that lives inside the browser, runs in the context of the current tab, and handles REST, GraphQL, and WebSocket connections without the overhead of a full application.

What API Testing PRO does

The extension adds an API testing panel accessible from the browser toolbar. You select a method (GET, POST, PUT, PATCH, DELETE), enter the URL, configure headers and body, and send. The response is displayed with syntax highlighting, status code, timing, and header inspection. It is essentially the fetch() console approach with a proper interface wrapped around it.

The key difference from web-based tools is execution context. Because the extension runs inside the browser, it can access cookies and session storage from the current domain. If you are logged into a web application and want to test an API endpoint that requires the same session cookie, the extension inherits that authentication automatically. You do not need to manually extract a token and paste it into a header field.

REST, GraphQL, and WebSocket support

REST testing covers all standard HTTP methods with full control over headers, query parameters, and request bodies. JSON bodies are auto-formatted with syntax highlighting in both the request and response panes.

The GraphQL interface provides a query editor with syntax highlighting and a variables panel. Point it at a GraphQL endpoint, write your query, define variables in a separate JSON panel, and execute. The response displays the data and errors objects separately for cleaner reading.

WebSocket testing lets you establish connections, send messages, and view the bidirectional message stream in real time. This is useful for debugging chat applications, live notification systems, and real-time data feeds without writing client code.

Lightweight by design

The extension uses Manifest V3 with a minimal permission set. It does not run background processes when you are not using it. The install size is under 500 KB, compared to Postman's multi-hundred-megabyte footprint. It stays out of your way until you need it, then provides a clean testing interface without loading a separate application or tab.

API Testing PRO currently has 6 users on the Chrome Web Store. I built it to solve my own workflow friction, and it remains a focused tool rather than a platform. If you want a lightweight, in-browser API tester that handles REST, GraphQL, and WebSocket without the overhead of Postman or the limitations of the console, it is worth trying.

Reading API Documentation Effectively

Good API testing starts before you send your first request. Reading documentation effectively is a skill that saves hours of trial and error, and most developers underinvest in it.

What to look for first

Start with the authentication section. Every other part of the documentation is useless if you cannot authenticate. Identify whether the API uses API keys, OAuth 2.0, Bearer tokens, Basic auth, or session cookies. Note where credentials go: headers, query parameters, or request body. Some APIs use multiple authentication methods for different endpoints or permission levels.

Next, read the rate-limiting section. Understand the limits per minute, per hour, and per day. Note whether rate limits apply per API key, per IP address, or per user. Check whether the API returns rate-limit headers (X-RateLimit-Remaining, X-RateLimit-Reset) that you can inspect in test responses.

Then review the error response format. A well-documented API describes its error codes and response structures. Knowing that a 422 means validation failed with field-specific error messages, while a 401 means your token expired, prevents unnecessary debugging. Pay attention to whether errors follow a consistent structure or vary by endpoint.

Base URL and versioning

Most APIs use versioned base URLs like https://api.example.com/v2/. Some use header-based versioning where you send Accept: application/vnd.example.v2+json. A few use query parameter versioning like ?version=2. Identify the versioning strategy before testing, because sending requests to the wrong version produces confusing results that look almost correct.

Pagination patterns

APIs that return collections almost always paginate. Common patterns include offset-based (?offset=20&limit=10), cursor-based (?cursor=abc123&limit=10), and page-based (?page=3&per_page=10). Cursor-based pagination is more reliable for data that changes frequently. The documentation should specify which pattern each endpoint uses, what the default page size is, and what the maximum allowed page size is.

Testing against sandbox environments

Many APIs provide sandbox or test environments with separate base URLs and credentials. Stripe uses https://api.stripe.com with test-mode API keys that start with sk_test_. PayPal provides a sandbox at https://api-m.sandbox.paypal.com. Always test against sandbox environments first. Sending test requests to production APIs risks creating real data, triggering real charges, or hitting production rate limits that affect actual users.

Common API Testing Mistakes

After years of testing APIs and helping other developers debug their integrations, I see the same mistakes repeatedly. Here are the nine that cause the most wasted time.

Forgetting the Content-Type header

This is the most common mistake by a wide margin. You send a POST request with a JSON body but forget to include Content-Type: application/json. The server receives the body as plain text, fails to parse it, and returns a 400 or 415 error. The fix is trivially simple, but the error message often does not mention Content-Type specifically, so developers waste time reviewing their JSON structure instead of their headers.

Sending the wrong Content-Type for the body format

Related to the above: sending Content-Type: application/x-www-form-urlencoded when the body is JSON, or vice versa. Form-encoded data uses key=value&key2=value2 format. JSON uses {"key":"value"}. Sending the wrong Content-Type for your body format produces parsing errors that are not always descriptive.

Ignoring CORS errors in the browser

CORS errors in the DevTools console do not mean the API is broken. They mean the browser is blocking the response because the API's server did not include the appropriate Access-Control-Allow-Origin header. The request actually reached the server and may have executed successfully. The browser simply refuses to expose the response to your JavaScript code. Use curl, Hoppscotch's proxy, or a dedicated API testing tool to bypass CORS when testing.

Not checking the HTTP status code

The Fetch API does not throw an error for 4xx or 5xx responses. A fetch() call that returns a 404 still resolves the promise successfully. You must check response.ok or response.status explicitly. Many developers assume that the absence of a catch() handler means the request succeeded, then spend time confused about why their response data is empty or contains an error message.

const response = await fetch('https://api.example.com/data');

// Wrong: assumes success
const data = await response.json();

// Right: check status first
if (!response.ok) {
  console.error(`HTTP ${response.status}:`, await response.text());
  return;
}
const data = await response.json();

Hardcoding authentication tokens

Pasting a token directly into a fetch() call in the console is fine for a quick test. Hardcoding that same token into source code, committing it to a repository, and pushing to GitHub is a security incident. Even private repositories should not contain raw tokens. Use environment variables, secrets managers, or configuration files excluded from version control.

Testing only the happy path

Sending a well-formed request with valid data and confirming it works is step one. It is not the complete test. Send requests with missing required fields. Send strings where numbers are expected. Send dates in the wrong format. Omit the authentication header. Send a request body that exceeds the size limit. These edge cases reveal how the API behaves under error conditions, which is exactly the information you need when building error handling in your integration code.

Not URL-encoding query parameters

Special characters in query parameter values must be URL-encoded. A space becomes %20 or +. An ampersand becomes %26. Failing to encode these characters corrupts the query string. In JavaScript, use encodeURIComponent() for individual values or the URLSearchParams API for building complete query strings:

const params = new URLSearchParams({
  query: 'hello world & goodbye',
  limit: '10',
  offset: '0',
});
const url = `https://api.example.com/search?${params.toString()}`;
// Result: https://api.example.com/search?query=hello+world+%26+goodbye&limit=10&offset=0

Assuming all 200 responses mean success

Some APIs return 200 OK for every response and indicate success or failure in the response body. The Slack Web API is a well-known example: every response returns 200, and you must check the ok field in the JSON body to determine whether the operation succeeded. Always inspect the response body, not just the status code.

Ignoring response headers

Response headers carry important metadata that developers often overlook. Rate-limit headers tell you how many requests remain before throttling. Pagination headers (like GitHub's Link header) provide URLs for the next and last pages. Cache headers indicate whether responses are stale. The Retry-After header tells you exactly how long to wait before retrying a rate-limited request. Inspect headers during testing so your integration code handles them properly.

Frequently Asked Questions

What is the fastest way to test an API in the browser?
Open DevTools with F12, go to the Console tab, and use fetch() with await inside an async IIFE. This requires zero installation, works in any browser, and returns formatted responses directly in the console. For APIs that block browser requests due to CORS, use a Chrome extension like API Testing PRO that can bypass origin restrictions.
Is Hoppscotch really free?
Yes. Hoppscotch is open source under the MIT license. The web version at hoppscotch.io is free with no account required for individual use. Team features (shared workspaces, collaboration) require a free account. The self-hosted community edition is also free. There is a paid cloud plan for larger teams that adds additional management features.
Can I test APIs with authentication from the browser console?
Yes. Add an Authorization header to your fetch() options with a Bearer token, API key, or Basic credentials. For cookie-based auth, if you are on the same domain as the API, include credentials: 'include' in your fetch options. Cross-origin requests with cookies require the server to set Access-Control-Allow-Credentials: true.
Why do I get CORS errors when testing APIs in the browser?
CORS errors occur when the API server does not include your browser's origin in its Access-Control-Allow-Origin response header. This is a browser security feature, not an API bug. The same request sent via curl, Postman, or a server-side script will succeed because those tools are not subject to browser CORS policies. Use a dedicated API testing tool or extension to bypass this restriction during development.
Should I use Postman or a lightweight alternative?
Use Postman when you need mock servers, automated test suites, API monitoring, or team collaboration features. For individual developers who primarily need to send requests and inspect responses, lighter tools like Hoppscotch, Thunder Client, or a browser extension consume fewer resources and start faster. Many developers use a lightweight tool for daily work and Postman only when they need its advanced features.
What is the difference between REST and GraphQL for API testing?
REST APIs expose multiple endpoints (one per resource) and return fixed response shapes. You test them by sending requests to specific URLs with specific HTTP methods. GraphQL APIs expose a single endpoint and let you specify exactly which fields you want in the response. Testing GraphQL requires writing queries in a specific syntax. Tools like Hoppscotch and API Testing PRO support both.
How do I test WebSocket connections?
WebSocket connections cannot be tested with regular HTTP tools. You need a tool that supports the WebSocket protocol directly. In the browser console, use the WebSocket constructor: new WebSocket('wss://example.com/socket'). For a graphical interface, Hoppscotch and API Testing PRO both provide dedicated WebSocket testing panels where you can connect, send messages, and view the bidirectional message stream.
Can curl handle all the same tests as Postman?
curl can send any HTTP request that Postman can. The difference is workflow, not capability. curl excels at scriptable, repeatable tests and CI/CD integration. Postman excels at exploratory testing with a visual interface, saved collections, and team collaboration. Postman can export any request as a curl command, and curl commands can be imported into Postman.
What API should I practice testing with?
JSONPlaceholder (jsonplaceholder.typicode.com) is the standard free fake API for testing. It supports GET, POST, PUT, PATCH, and DELETE operations with realistic response data. The GitHub API is excellent for testing authenticated requests with real data. httpbin.org echoes back whatever you send, making it ideal for verifying that your requests are formatted correctly.
