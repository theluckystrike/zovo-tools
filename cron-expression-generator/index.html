Definition

A cron expression is a string of five (or six) fields representing a schedule for recurring tasks in Unix-like operating systems. The five fields are minute, hour, day of month, month, and day of week. Cron is a time-based job scheduler that executes commands at specified intervals, commonly used for system maintenance, backups, and automated deployments.

Understanding Cron Scheduling

I built this cron expression generator because I found myself constantly looking up cron syntax while configuring scheduled tasks. Cron is the time-based job scheduler present in virtually every Unix-like operating system, and its scheduling syntax has become the standard for automated task scheduling across the entire software industry.

The name "cron" comes from the Greek word "chronos" meaning time. The cron daemon runs continuously in the background and checks the crontab (cron table) file every minute to see if any scheduled tasks need to execute. Each line in the crontab represents one scheduled job, consisting of a timing specification (the cron expression) followed by the command to run.

How the Five Fields Work Together

The five fields of a cron expression work as an AND condition. All five conditions must be true simultaneously for the job to run. When the minute field says "0", the hour field says "9", and all other fields are asterisks, the job runs when the minute is 0 AND the hour is 9, which happens once per day at 9:00 AM.

There is one exception to the AND rule: the day of month and day of week fields work as an OR condition when both are specified (not asterisks). The expression 0 0 15 * 1 runs at midnight on the 15th of every month OR every Monday, not only on Mondays that fall on the 15th. This behavior is a common source of confusion and bugs in cron scheduling.

The Step Operator (Slash)

The slash operator is one of the most useful features in cron syntax. It defines a step value within a range. */5 in the minute field means "every 5th minute" and is equivalent to 0,5,10,15,20,25,30,35,40,45,50,55. You can combine the step operator with a range: 10-50/5 means every 5 minutes from minute 10 to minute 50 (10, 15, 20, 25, 30, 35, 40, 45, 50).

Step values work with all five fields. In the hour field, */6 means every 6 hours (0, 6, 12, 18). In the day of month field, */7 means every 7 days starting from day 1 (1, 8, 15, 22, 29). In the month field, */3 means every 3 months (1, 4, 7, 10), which creates a quarterly schedule.

Common Scheduling Patterns

Based on my experience managing servers and CI/CD pipelines, these are the most frequently used cron patterns. Database backups typically run daily during low-traffic hours, usually between 1 AM and 4 AM. A common expression is 0 2 * * * for a 2 AM daily backup. Log rotation often runs weekly on Sunday night with 0 0 * * 0. Monitoring checks frequently run every 5 or 10 minutes with */5 * * * * or */10 * * * *.

For business applications, report generation commonly runs on weekday mornings with 0 8 * * 1-5 (8 AM Monday-Friday). Billing processes often run monthly on the first with 0 1 1 * * (1 AM on the 1st). Newsletter sends might use 0 10 * * 2 (10 AM every Tuesday).

Cron in Different Systems

While the five-field cron format is standard across most Unix-like systems, different platforms have slight variations. Linux uses the standard five-field format in /etc/crontab and user crontabs managed with crontab -e. macOS supports the same format but increasingly encourages launchd plist files for scheduled tasks. Most cloud platforms (AWS CloudWatch, Google Cloud Scheduler, Azure Functions) support the standard five-field format.

Some systems extend the standard format. The Quartz Scheduler (used in Java applications and Spring Framework) adds a seconds field at the beginning, making it a six-field format. AWS EventBridge uses a six-field format where the first field represents minutes and the sixth represents years. Jenkins uses a modified cron syntax with an additional "H" symbol for hash-based distribution to prevent all jobs from starting at the same time.

Kubernetes CronJobs use the standard five-field format. GitHub Actions uses it in workflow schedules. GitLab CI/CD pipeline schedules use it. Docker and Docker Compose support it through various timer mechanisms. Understanding the five-field format gives you the foundation to work with scheduling across virtually any platform.

Best Practices for Cron Scheduling

Based on years of managing production systems, I have developed these practices that prevent common cron-related problems. First, avoid scheduling multiple heavy jobs at the same time. Many administrators default to midnight (0 0 * * *) for daily jobs, creating a "thundering herd" of simultaneous resource-intensive processes. Spread jobs across different times to avoid resource contention.

Second, always redirect output and log errors. A cron job that fails silently can cause data loss or system issues that go undetected for days. Append >> /var/log/myjob.log 2>&1 to your cron commands to capture both standard output and error output in a log file.

Third, use file locks (flock) to prevent overlapping executions. If a job takes longer than expected and is still running when the next execution is scheduled, you can end up with multiple instances competing for the same resources. The flock command in Linux prevents this by acquiring an exclusive lock before execution.

Fourth, set the proper PATH and environment variables in your crontab. Cron runs with a minimal environment that may not include paths to executables your scripts depend on. Either use absolute paths in your commands or set the PATH variable at the top of your crontab file.

Fifth, test cron expressions before deploying to production. Use this generator to verify your expression produces the expected run times. A single mistake in a cron expression can cause a job to run 60 times per hour instead of once per hour, potentially overwhelming your system.

Timezone Considerations

Cron jobs run based on the system's local timezone by default. This can cause unexpected behavior during daylight saving time transitions. When clocks spring forward, a job scheduled for the skipped hour will not run. When clocks fall back, a job scheduled during the repeated hour may run twice. For time-sensitive jobs, consider using UTC to avoid these issues.

In many Linux distributions, you can set the timezone for the entire crontab by adding TZ=UTC or TZ=America/New_York at the top of the file. Cloud-based cron services like AWS CloudWatch Events and Google Cloud Scheduler allow timezone specification per schedule, giving you more granular control.

For distributed systems operating across multiple timezones, I recommend standardizing all scheduled jobs on UTC and converting to local times only for display purposes. This eliminates ambiguity and prevents the daylight saving time issues that have caused outages at even major technology companies.

Monitoring and Debugging Cron Jobs

When a cron job fails to run, the debugging process starts with verifying the cron expression itself. Use this generator to confirm the expression matches your intended schedule. Then check the system cron log (usually /var/log/cron or /var/log/syslog) to see if the cron daemon attempted to execute the job. Common issues include permission problems, missing executables, incorrect file paths, and environment variable differences between your interactive shell and the cron environment.

For critical cron jobs, I recommend implementing a "dead man's switch" monitoring pattern. Services like Healthchecks.io or Cronitor provide URLs that your cron job should ping upon successful completion. If the expected ping does not arrive within a configured time window, the service sends an alert. This catches both jobs that fail to start and jobs that start but crash before completing.

Alternatives to Cron

While cron remains the most widely used scheduler, modern alternatives address some of its limitations. Systemd timers offer better logging, dependency management, and timezone support on Linux systems. They can also trigger on events other than time, such as system boot or hardware changes. Apache Airflow provides workflow orchestration with dependency graphs, retries, and monitoring for complex data pipeline scheduling.

For application-level scheduling, libraries like node-cron (Node.js), APScheduler (Python), and Quartz (Java) embed scheduling directly in application code, making it easier to manage alongside business logic. Kubernetes CronJobs provide container-based scheduling with automatic retry and resource management in containerized environments.

Despite these alternatives, the cron expression format itself has become a universal standard. Most of these alternative tools accept cron expressions for defining schedules, so learning cron syntax remains valuable regardless of which specific scheduling tool you use.

Security Considerations

Cron jobs run with the permissions of the user who created them. System-level crontabs (/etc/crontab) typically run as root, making them a potential security risk if misconfigured. Follow the principle of least privilege by running jobs as non-root users whenever possible. Never store passwords or API keys directly in crontab entries. Instead, reference environment variables or secure credential stores.

The /etc/cron.allow and /etc/cron.deny files control which users can create cron jobs. In security-sensitive environments, use cron.allow to whitelist only authorized users rather than relying on cron.deny to blacklist specific users. Regularly audit user crontabs with crontab -l -u username to identify unauthorized or outdated scheduled tasks.

Environment Variable Pitfalls

One of the most common reasons cron jobs fail is the difference between the cron environment and your interactive shell environment. When you log into a terminal, your shell sources configuration files like .bashrc, .bash_profile, or .zshrc, setting up PATH, language variables, and custom environment variables. Cron does not source any of these files. It starts with a minimal environment that typically only includes HOME, LOGNAME, PATH (often just /usr/bin:/bin), and SHELL.

This means commands that work perfectly when you run them manually may fail under cron because the executable is not found on the cron PATH. For example, if you installed Node.js via nvm, the node binary lives in a nvm-managed directory that is not on the default cron PATH. The fix is to either use absolute paths in your cron commands (like /home/user/.nvm/versions/node/v18.17.0/bin/node script.js) or set the PATH variable at the top of your crontab file.

You can set environment variables in the crontab itself. Add lines like PATH=/usr/local/bin:/usr/bin:/bin and NODE_ENV=production before your scheduled entries. These variables apply to all jobs that follow them in the crontab. Alternatively, wrap your cron command in a shell script that sources the necessary environment before executing the actual task.

Cron Job Output and Email

By default, cron emails the output (both stdout and stderr) of every job to the user who owns the crontab. On many systems this means unread emails accumulating in a local mailbox that nobody checks. If your jobs produce output and you want to capture it for debugging, redirect stdout and stderr to a log file: 0 2 * * * /path/to/script.sh >> /var/log/myscript.log 2>&1. The 2>&1 part redirects stderr to the same destination as stdout.

To suppress all output from a cron job, redirect to /dev/null: 0 2 * * * /path/to/script.sh > /dev/null 2>&1. Be cautious with this approach because it hides error messages that could help you diagnose failures. A better practice is to log output but implement log rotation to prevent log files from growing indefinitely. The logrotate utility on Linux can manage cron job logs automatically.

You can change the email recipient by setting the MAILTO variable in your crontab. Setting MAILTO="" disables email notifications entirely. Setting MAILTO="admin@example.com" sends output to a specific address. You can specify multiple recipients separated by commas.

Cron vs Systemd Timers

Modern Linux distributions based on systemd offer an alternative scheduling mechanism called systemd timers. While cron uses a single configuration format (the crontab), systemd timers require two unit files: a service unit that defines what to run, and a timer unit that defines when to run it. This separation provides better modularity but adds complexity compared to cron's single-line job definitions.

Systemd timers offer several advantages over cron. They support calendar-based scheduling with a more readable syntax (like Mon *-*-* 09:00:00 for every Monday at 9 AM). They integrate with journald for centralized logging, eliminating the need for manual output redirection. They can trigger on events other than time, such as boot completion or hardware changes. They support accuracy settings that allow the system to batch timer events for power efficiency.

However, cron remains the more portable option. Cron works on every Unix-like system including macOS, FreeBSD, and older Linux distributions. The five-field cron syntax is understood by virtually every developer, while systemd timer syntax has a steeper learning curve. For simple scheduled tasks, cron is still the most practical choice. For complex scheduling requirements with dependency chains, logging needs, and event-based triggers, systemd timers may be worth the additional setup effort.

Cron Expression Patterns for Specific Use Cases

Database maintenance is one of the most common use cases for cron scheduling. For PostgreSQL, I typically schedule VACUUM ANALYZE during off-peak hours with 0 3 * * * (3 AM daily). Full VACUUM operations that lock tables should run on weekends with 0 2 * * 0 (2 AM Sunday). For MySQL, improve tables weekly and run incremental backups daily with differential schedules to avoid resource conflicts.

Log management requires thoughtful scheduling. Application logs can grow rapidly, so I schedule log rotation every 6 hours with 0 */6 * * * and log archival daily with 30 1 * * * (1:30 AM). Old log archives can be cleaned up monthly on the 1st with 0 4 1 * * (4 AM). Separating these tasks by at least 30 minutes prevents I/O contention.

SSL certificate renewal with Let's Encrypt is commonly automated via cron. The recommended practice is to attempt renewal twice daily with 0 0,12 * * * (midnight and noon). Let's Encrypt certificates have a 90-day validity period, and the certbot client only renews certificates that are within 30 days of expiration, so the frequent checks have minimal overhead while ensuring timely renewal.

Monitoring and health checks are another frequent use case. For uptime monitoring, */5 * * * * (every 5 minutes) is a common interval. For disk space warnings, */30 * * * * (every 30 minutes) catches growing partitions before they fill up. For daily summary reports, 0 8 * * 1-5 (8 AM weekdays) delivers information when the team starts work.

Month and Day Name Support

Some cron implementations accept three-letter month and day names instead of numbers. Instead of 0 9 * 1 * you can write 0 9 * JAN *. Instead of 0 9 * * 1 you can write 0 9 * * MON. While this improves readability, it reduces portability since not all cron implementations support name syntax. The standard POSIX cron specification only defines numeric values, so the safest approach is to stick with numbers for maximum compatibility.

Month names that work on most systems: JAN, FEB, MAR, APR, MAY, JUN, JUL, AUG, SEP, OCT, NOV, DEC. Day names: SUN, MON, TUE, WED, THU, FRI, SAT. Names are case-insensitive on most implementations but using uppercase is the conventional style. You can mix names with other operators: 0 9 * JAN-MAR MON-FRI runs at 9 AM on weekdays in the first quarter.

Hash Symbol in Jenkins Cron

Jenkins introduced the "H" symbol (hash) to its cron syntax, which is not part of standard cron. The H symbol distributes load by using a consistent hash of the job name to determine the actual trigger time within the specified range. The expression H * * * * runs once per hour at a minute determined by the job's hash, preventing all jobs from triggering at minute 0 simultaneously.

Jenkins also supports H/15 * * * * to run approximately every 15 minutes, with the exact times varying by job. The syntax H(0-29)/10 * * * * constrains the hash to the first 30 minutes. Convenience aliases like @daily, @weekly, @monthly, and @yearly work in both Jenkins and standard cron. Jenkins adds @midnight which triggers between 12:00 AM and 2:59 AM using the hash mechanism.

Crontab Management Commands

Managing crontab entries involves a few important commands. crontab -e opens the current user's crontab in the default editor. crontab -l lists all current entries. crontab -r removes the entire crontab, so use it carefully. crontab -u username -l lists another user's crontab (requires root privileges).

For system administrators managing multiple servers, I recommend version-controlling crontab files. Export the current crontab with crontab -l > crontab.backup, store it in a git repository, and restore it with crontab crontab.backup. This approach provides an audit trail of scheduling changes and makes it easy to replicate configurations across servers.

The system-wide crontab at /etc/crontab has a slightly different format from user crontabs. It includes a sixth field between the schedule and the command that specifies which user should run the command. For example, 0 3 * * * root /usr/local/bin/backup.sh runs the backup script as the root user at 3 AM daily. The directories /etc/cron.daily, /etc/cron.weekly, and /etc/cron.monthly provide a simpler alternative where you just drop scripts into the appropriate directory without writing cron expressions at all.

Common Mistakes and How to Avoid Them

The most frequent cron mistake I encounter is forgetting that the day-of-month and day-of-week fields are OR-combined when both are non-asterisk. The expression 0 9 15 * 1 does not mean "9 AM on the 15th if it falls on a Monday." It means "9 AM on the 15th of every month AND 9 AM every Monday." This catches many developers off guard and can cause jobs to run more frequently than intended.

Another common mistake is using 0 0 * * 7 for Sunday, assuming the day-of-week field is 1-indexed. While day 7 does represent Sunday on many Linux implementations (being equivalent to day 0), this is not universally supported. The POSIX standard defines 0 as Sunday. Using 0 0 * * 0 is safer and more portable.

The step operator also causes confusion. 0-23/2 and */2 in the hour field both produce the same result (even hours), but 1-23/2 produces odd hours. The starting value matters. In the day-of-month field, */7 triggers on days 1, 8, 15, 22, and 29, not every 7 days from the last execution. This distinction between "every Nth matching value" and "every N days since last run" is a important concept to understand.

Forgetting to escape percent signs is another frequent issue. In crontab entries, the percent sign (%) has special meaning. It is treated as a newline, and everything after the first unescaped percent sign is passed as standard input to the command. This causes problems with commands that use date formatting like date +%Y-%m-%d. You must escape percent signs as \% in crontab entries: 0 0 * * * /path/to/script.sh >> /var/log/backup-$(date +\%Y-\%m-\%d).log 2>&1.

Cron in Cloud Environments

Cloud platforms have adapted cron syntax for their scheduling services. AWS CloudWatch Events (now EventBridge) uses a six-field cron format where the sixth field represents the year. AWS also uses a question mark (?) in either the day-of-month or day-of-week field to indicate "no specific value," which resolves the OR-combination ambiguity of standard cron. Google Cloud Scheduler supports standard five-field cron with timezone specification per job. Azure Functions use a six-field format with seconds as the first field, similar to Quartz.

Serverless architectures use cron expressions for triggering functions on a schedule. AWS Lambda functions can be triggered by EventBridge rules with cron expressions. Google Cloud Functions support cron via Cloud Scheduler. Azure Functions have timer triggers that accept cron expressions. In all these cases, the underlying cron syntax is the same, making your knowledge transferable across cloud providers.

Container orchestration platforms like Kubernetes provide CronJob resources that accept standard five-field cron expressions. Kubernetes adds concurrency policies (Allow, Forbid, Replace) that control behavior when a job is still running at the next scheduled time. The startingDeadlineSeconds field specifies how long past the scheduled time a job can start, handling cases where the scheduler was temporarily unavailable.

Performance Impact of Cron Scheduling

Poorly scheduled cron jobs can cause significant performance problems. I have seen production systems where dozens of jobs were all scheduled at the top of the hour (0 * * * *), creating periodic load spikes that affected user-facing services. Staggering job start times by even a few minutes can dramatically reduce resource contention. Instead of scheduling all hourly jobs at minute 0, distribute them: 2 * * * * for job A, 7 * * * * for job B, 13 * * * * for job C.

For jobs that process large datasets, consider splitting the workload across multiple scheduled executions. Instead of one daily job that processes 24 hours of data at midnight, run 24 hourly jobs that each process one hour of data. This reduces peak memory usage, shortens individual job duration, and makes failures easier to recover from since only one hour of data needs reprocessing.

CPU-intensive cron jobs should use nice to lower their scheduling priority: 0 2 * * * nice -n 19 /path/to/heavy-job.sh. The nice value of 19 gives the job the lowest possible priority, ensuring it does not interfere with interactive processes or higher-priority services. For I/O-intensive jobs, ionice provides similar control over disk access priority.

Testing Cron Expressions Safely

Before deploying a new cron job to production, I recommend a multi-step testing process. First, use this generator to verify the expression produces the expected schedule. Check the next 10 run times to confirm they match your intentions. Second, test the command manually in a terminal that mimics the cron environment by unsetting most environment variables: env -i PATH=/usr/bin:/bin HOME=$HOME /path/to/your/command.sh. This reveals environment-dependent failures before they happen in production.

Third, deploy the job with verbose logging for the first few executions. Add timestamps and execution markers to your log output so you can verify the job ran at the expected times. Fourth, set up monitoring alerts for the job using a dead man's switch service. Only after confirming correct behavior over several scheduled cycles should you consider the deployment complete.

For complex scheduling requirements, consider creating a test crontab that runs the same job at accelerated intervals. If you want to test a weekly job, temporarily schedule it every 5 minutes to verify the script works correctly, then change the schedule to the intended weekly timing once you are satisfied with the results.

Additional Cron Patterns and Recipes

Some scheduling requirements demand creative use of cron syntax. Running a job every 90 minutes cannot be expressed with a single cron entry because 90 does not divide evenly into 60 minutes or 24 hours. The workaround is to use multiple crontab entries: 0 0,3,6,9,12,15,18,21 * * * and 30 1,4,7,10,13,16,19,22 * * * together give you roughly 90-minute intervals. For exact 90-minute intervals, a persistent process with its own timer is more appropriate than cron.

Running a job on the last day of every month is another common requirement that cron cannot express directly. The day-of-month field has a maximum of 31, but months have different lengths. The standard workaround is to use a shell conditional: 55 23 28-31 * * [ "$(date -d tomorrow +\%d)" = "01" ] && /path/to/script.sh. This checks if tomorrow is the first day of the next month, which means today is the last day of the current month. The cron expression runs at 11:55 PM on days 28 through 31, and the shell conditional ensures the script only executes on the actual last day.

Running a job on the Nth weekday of a month is similarly impossible in standard cron syntax. For "the second Tuesday of every month," you can approximate with 0 9 8-14 * 2 which runs at 9 AM on Tuesdays that fall between the 8th and 14th. However, because day-of-month and day-of-week are OR-combined, this expression also runs on days 8-14 regardless of the day of week. A shell conditional is again needed for precision.

Cron in Docker Containers

Running cron inside Docker containers requires special considerations. The default cron daemon expects to run as PID 1, but in containers, the application process typically holds that position. The recommended approach is to use a process manager like supervisord to run both your application and the cron daemon, or to use a dedicated cron container that executes tasks via docker exec commands on other containers.

When building a Docker image that includes cron, install the cron package and copy your crontab file during the build process. A typical Dockerfile snippet includes COPY crontab /etc/cron.d/app-cron, RUN chmod 0644 /etc/cron.d/app-cron, and RUN crontab /etc/cron.d/app-cron. The crontab file must end with a newline character, or cron will silently ignore it. This is a common gotcha that causes hours of debugging.

Environment variables set with docker run -e or in docker-compose.yml are not automatically available to cron jobs inside the container. The cron daemon starts independently and does not inherit the container's environment. A common workaround is to dump the environment to a file at container startup (env > /etc/environment) and source it in your cron job scripts.

Cron Job Dependency Chains

Complex workflows often require multiple cron jobs to run in sequence, with each job depending on the successful completion of the previous one. Standard cron does not support job dependencies natively. The simplest approach is to chain jobs by scheduling them at staggered times with sufficient buffer: job A at 1:00 AM, job B at 1:30 AM, job C at 2:00 AM. This works but wastes time if jobs finish early and fails if jobs run longer than expected.

A more dependable approach uses sentinel files. Job A creates a flag file upon successful completion. Job B checks for this flag file before proceeding. If the flag file does not exist, job B exits without performing any work. This pattern ensures job B only runs after job A completes successfully, regardless of how long job A takes. Remember to clean up sentinel files to prevent stale flags from causing issues.

For complex dependency management, workflow orchestration tools like Apache Airflow, Prefect, or Dagster provide directed acyclic graph (DAG) definitions with automatic retry, alerting, and dependency resolution. These tools still use cron expressions for the initial trigger schedule but handle all downstream dependencies programmatically. If your scheduling needs have grown beyond simple cron entries, investing in a proper workflow orchestrator will save you significant debugging time.

Cron and Internationalization

Cron expressions themselves are timezone-agnostic. The five fields define a schedule relative to the system clock, and the system clock determines which timezone is in effect. This simplicity is both a strength and a limitation. For applications serving users in a single timezone, the system timezone is usually configured to match, and cron schedules work as expected.

For globally distributed applications, a single cron schedule produces different local times in different regions. A job scheduled at 0 9 * * * runs at 9 AM system time, which could be 9 AM UTC, 9 AM Eastern, or 9 AM Tokyo depending on the server's timezone configuration. When consistency across regions is required, the best practice is to set all cron jobs to UTC and handle timezone conversion in the application logic.

Some systems support per-crontab timezone settings. GNU cron allows you to prepend TZ=America/New_York at the top of the crontab file, and all subsequent entries will be evaluated in that timezone. Cloud scheduling services like Google Cloud Scheduler allow timezone specification per individual job, providing the most granular control. Always document which timezone your cron jobs are configured for, as this information is valuable for debugging scheduling issues.

Frequently Asked Questions

What is a cron expression?

A cron expression is a string of five fields separated by spaces that defines a recurring schedule. The fields represent minute (0-59), hour (0-23), day of month (1-31), month (1-12), and day of week (0-6, where 0 is Sunday). Each field can contain specific values, wildcards (*), ranges (1-5), lists (1,3,5), or step values (*/5). The expression determines when a scheduled task should execute.

How do I run a cron job every 5 minutes?

Use the expression */5 * * * * which means every 5th minute of every hour, every day. The */5 in the minute field uses the step operator to run at minutes 0, 5, 10, 15, 20, 25, 30, 35, 40, 45, 50, and 55. You can change the step value to any number. For example, */10 runs every 10 minutes, */15 every 15 minutes, and */30 every 30 minutes.

What does the asterisk mean in cron?

The asterisk (*) is a wildcard meaning every possible value for that field. An asterisk in the minute field means every minute (0 through 59). In the hour field, every hour (0 through 23). In the day of month field, every day (1 through 31). In the month field, every month (1 through 12). In the day of week field, every day of the week (0 through 6). Most cron expressions have at least two or three asterisks.

What is the difference between 5-field and 6-field cron?

Standard Unix cron uses 5 fields covering minute, hour, day of month, month, and day of week. Some systems add a seconds field at the beginning (Quartz Scheduler, Spring) or a year field at the end (AWS EventBridge). This tool uses the standard 5-field format that works with Linux crontab, macOS, Kubernetes CronJobs, GitHub Actions, and most CI/CD platforms.

How do I schedule a cron job for weekdays only?

Set the fifth field (day of week) to 1-5, representing Monday through Friday. For example, 0 9 * * 1-5 runs at 9:00 AM every weekday. To run on weekends only, use 0,6 in the day of week field (0 is Sunday, 6 is Saturday). The expression 0 10 * * 0,6 runs at 10:00 AM on Saturday and Sunday.
